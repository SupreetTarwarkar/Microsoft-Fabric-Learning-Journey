# Chapter 11: Power BI, Semantic Models and Report Security

---

## 11.1 Power BI Reporting Layer

After data has moved through engineering and modelling stages, the final goal is to make the data useful to business users.

The complete Fabric analytical flow can be understood as:

```text
Source Data
     ↓
Pipeline / Dataflow / Notebook
     ↓
Bronze
     ↓
Silver
     ↓
Gold
     ↓
Fact + Dimension Tables
     ↓
Semantic Model
     ↓
Power BI Report
     ↓
Power BI Service / App
     ↓
Business Users
```

Power BI acts as the **reporting and analytical consumption layer** of the overall Fabric solution.

This stage is mainly concerned with:

- Business questions
- KPIs
- Measures
- Visuals
- User interaction
- Security
- Validation
- Distribution

### Important Understanding

Reporting should not be viewed as an isolated activity.

The quality of the final report depends on the quality of:

```text
Data Engineering
      +
Data Transformation
      +
Data Modelling
      +
Semantic Model
      +
Reporting
```

A poor upstream data model can create problems in Power BI even if the report looks visually attractive.

## 11.2 Power BI Report

A **Power BI Report is an interactive collection of visuals built on top of a Semantic Model.**

A report can contain:

- KPI Cards
- Bar Charts
- Column Charts
- Line Charts
- Tables
- Matrix visuals
- Slicers
- Maps
- Drill-through pages
- Tooltips
- Filters
- Interactive navigation

The report is primarily the:

> **Presentation + Analysis layer**

The underlying analytical logic should ideally already be structured properly in the Semantic Model.

### Simple Flow

```text
Semantic Model
      ↓
Power BI Report
      ↓
Visual Analysis
      ↓
Business User
```

The report allows business users to interact with measures and dimensions without needing to understand the complete engineering architecture behind the data.

## 11.3 Report vs Semantic Model

These two concepts should not be confused.

### Semantic Model

The Semantic Model contains the analytical structure.

It can contain:

- Tables
- Relationships
- Measures
- Business logic
- Security roles
- Metadata

### Report

The Report uses the Semantic Model to create:

- KPIs
- Charts
- Tables
- Filters
- Slicers
- Interactive analysis

### Simple Understanding

> **Semantic Model = Analytical Brain**

> **Report = Visual Presentation**

### Architecture

```text
Gold / Warehouse / Lakehouse
            ↓
      Semantic Model
            ↓
Relationships
Measures
Business Logic
Security
            ↓
       Power BI Report
            ↓
        Business User
```

A report should ideally consume a well-designed Semantic Model rather than containing unnecessary analytical complexity directly in the visual layer.

## 11.4 Business-Question-Driven Reporting

A report should not be created by randomly adding visuals.

The first question should be:

> **What does the business actually want to know?**

For example, in a Sales report:

- What is Total Revenue?
- How many Orders were received?
- Which Products generate the most revenue?
- Which Region performs best?
- How is Revenue changing over time?
- Which Customers contribute the most?

Once the business question is clear, we can decide:

```text
Business Question
       ↓
KPI / Measure
       ↓
Appropriate Visual
```

Not:

```text
Available Visual
       ↓
Find Some Data to Put Inside It
```

### Report Design Flow

A useful report-building process is:

#### Step 1 — Understand Business Requirement

Identify:

- Business questions
- KPIs
- Target audience
- Required filters
- Required level of detail

#### Step 2 — Validate Data Model

Check:

- Fact tables
- Dimension tables
- Relationships
- Date table
- Grain

#### Step 3 — Create Measures

Examples:

```text
Total Revenue
Total Orders
Average Order Value
```

#### Step 4 — Build Report Layout

Decide:

- KPI section
- Trend section
- Breakdown analysis
- Filters
- Detailed analysis

#### Step 5 — Add Interactivity

Use:

- Slicers
- Cross-filtering
- Drill-through
- Tooltips
- Navigation

#### Step 6 — Validate Numbers

Compare Power BI results with:

- SQL
- Source data
- Validated analytical tables

#### Step 7 — Apply Security

Use RLS where required.

#### Step 8 — Publish and Distribute

Use:

- Power BI Service
- Power BI Apps

### Practical Principle

> **Business Question → Measure → Visual → Validation → Security → Distribution**

## 11.5 Measures vs Calculated Columns

Measures and Calculated Columns serve different purposes.

### Calculated Column

A Calculated Column is evaluated row by row and stored as part of the model.

Example:

```DAX
Revenue =
Sales[Quantity] * Sales[UnitPrice]
```

### Measure

A Measure is evaluated dynamically according to the current filter context.

Example:

```DAX
Total Revenue =
SUM(Sales[Revenue])
```

### Simple Difference

> **Calculated Column = Row-Level Stored Calculation**

> **Measure = Dynamic Analytical Calculation**

### Example

Suppose:

```text
Total Revenue = ₹10M
```

If the user selects:

```text
Region = West
```

the same measure may return:

```text
₹3M
```

The measure itself has not changed.

Its result changes because the filter context changed.

### Practical Understanding

For report KPIs and aggregations that need to respond to:

- Slicers
- Filters
- Visual selections
- Dimensions

Measures are generally the appropriate analytical approach.

---

## 11.6 Filter Context

**Filter Context determines which subset of data is evaluated by a DAX measure.**

Suppose the measure is:

```DAX
Total Revenue =
SUM(FactSales[Revenue])
```

Without filters:

```text
Total Revenue = ₹10M
```

Select:

```text
Region = West
```

Result:

```text
₹3M
```

Then select:

```text
Region = West
Year = 2026
```

Result might become:

```text
₹2M
```

### Important Understanding

> **The DAX measure stays the same, but the result changes according to Filter Context.**

This is one of the fundamental concepts behind interactive Power BI reporting.

### Filter Context Can Come From

- Slicers
- Visual filters
- Page filters
- Report filters
- Dimension selections
- Cross-filtering
- Drill-through context

## 11.7 Dimensions and Facts

A properly modelled Power BI solution commonly contains:

```text
             DimProduct
                  |
                  |
DimCustomer — FactSales — DimDate
                  |
                  |
               DimRegion
```

### Dimensions

Dimensions provide descriptive context.

Examples:

- Product
- Customer
- Date
- Region

They are commonly used in:

- Slicers
- Axes
- Rows
- Columns
- Filters

### Facts

Fact tables contain measurable business events and values.

Examples:

- Revenue
- Quantity
- Orders
- Cost

### Example

```text
DimProduct[Category]
       +
Total Revenue
```

produces:

```text
Revenue by Category
```

### Important Model Rule

> **Dimensions provide context; Facts provide measurements.**

Another useful rule is:

> **Dimensions filter Facts → Measures summarize Facts**

| Requirement | Suitable Visual |
|---|---|
| Single KPI | Card |

| Detailed records | Table |
| Hierarchical comparison | Matrix |
| Geographic analysis | Map |
| Report filtering | Slicer |
| Contribution comparison | Bar / Column; Pie/Donut when categories are limited |

### Practical Principle

> **Choose the simplest visual that answers the business question clearly.**

A more complicated visual is not automatically better.

### Example

Business question:

> Which Product Category generates the highest Revenue?

Possible visual:

```text
Bar Chart
```

Business question:

> How is Revenue changing over time?

Possible visual:

```text
Line Chart
```

Business question:

> What is Total Revenue?

Possible visual:

```text
Card
```

## 11.11 Date Table in Reporting

The Date Dimension created during data modelling becomes important during report building.

Suppose Sales transactions exist on:

```text
1 Aug
2 Aug
4 Aug
```

but no Sales occurred on:

```text
3 Aug
```

If the report uses only transaction dates:

```text
1 Aug
2 Aug
4 Aug
```

3 August may disappear.

A proper Date Dimension contains:

```text
1 Aug
2 Aug
3 Aug
4 Aug
```

This allows the report to maintain a continuous timeline.

### Why This Matters

Without a continuous Date table, the user may not know whether:

- No transactions occurred
- Data is missing
- A filter removed the date
- The source failed to load

### Important Understanding

> **The Date Table provides the calendar. It does not create missing transactions.**

Depending on the measure and visualization, a date with no transaction may display:

```text
0
```

or:

```text
Blank
```

## 11.12 Slicers

A **Slicer allows users to interactively filter report data.**

Common examples include:

- Year
- Month
- Region
- Product Category
- Customer Segment

### Example

Initial KPI:

```text
Total Revenue = ₹10M
```

User selects:

```text
Region = West
```

The report may then update to:

```text
Total Revenue = ₹3M
```

Other visuals also update according to the selected context.

### Why Slicers Are Useful

Slicers allow one report to support many analytical views.

Instead of creating:

```text
West Report
East Report
North Report
South Report
```

a single report can allow users to interactively select the required Region.

## 11.13 Dynamic Report Titles

Report titles can be made dynamic so users understand the current report context.

### Static Title

```text
Sales Analysis
```

This remains unchanged regardless of slicer selection.

### Dynamic Title

If the user selects:

```text
West
```

the title can become:

```text
Sales Analysis - West Region
```

If the user selects:

```text
North
```

it can become:

```text
Sales Analysis - North Region
```

### Why Dynamic Titles Are Useful

They answer:

> **What data am I currently looking at?**

This is particularly useful when:

- Slicers are active
- Screenshots are shared
- Reports are exported
- Multiple dimensions affect context

### Example Dynamic Title Measure

```DAX
Report Title =
"Sales Analysis - "
    & SELECTEDVALUE(
        DimRegion[Region],
        "All Regions"
    )
```

Possible result:

```text
Sales Analysis - All Regions
```

or:

```text
Sales Analysis - West
```

### Static vs Dynamic Information

**Static**

```text
Sales Performance Dashboard
```

**Dynamic**

```text
Sales Performance - Mumbai - 2026
```

Dynamic reporting can make the current context immediately visible to the user.

## 11.15 Report Validation

A Power BI report should be validated before publishing.

Suppose SQL returns:

```text
Total Revenue = ₹10,250,000
```

Power BI should return:

```text
Total Revenue = ₹10,250,000
```

when equivalent logic and filters are applied.

If values do not match, investigate:

- Relationships
- Filters
- Duplicate rows
- DAX logic
- Data types
- Model grain
- Transformation logic

### Important Principle

> **A beautiful dashboard with incorrect numbers is still an incorrect dashboard.**

### Validation Checklist

Before publishing, verify:

- KPI totals
- Trend totals
- Filters
- Slicer behavior
- Date filtering
- Relationships
- RLS behavior
- Dynamic titles
- Business logic

### Technical Success vs Business Correctness

A report loading successfully means:

```text
Technical Success
```

It does not automatically mean:

```text
Business Correctness
```

Both must be validated.

## 11.16 Row-Level Security

**Row-Level Security (RLS) controls which rows of data a user is allowed to access through the Semantic Model.**

Suppose one Sales report contains all Regions.

Business requirement:

```text
North Manager → North Data Only

South Manager → South Data Only

East Manager → East Data Only

West Manager → West Data Only
```

Instead of creating separate reports for every manager, RLS can control which rows each user is allowed to see.

### Simple Understanding

> **Same Report + Different Users = Different Allowed Data**

### RLS Works Through the Semantic Model

Conceptually:

```text
User
  ↓
Power BI Report
  ↓
Semantic Model
  ↓
RLS
  ↓
Allowed Data
  ↓
Visuals
```

Therefore:

> **RLS protects rows through the Semantic Model.**

### Hiding a Visual is Not Security

Suppose salary information exists in the model.

Simply:

- Hiding a visual
- Moving a visual to another page
- Hiding navigation

does not provide proper data security.

### Important Distinction

> **RLS = Restricts Rows**

Restricting specific tables or columns is a different type of security requirement.

### Workspace Role Consideration

RLS should be considered together with the overall access design.

Users should receive only the permissions they require.

This connects to the earlier:

> **Principle of Least Privilege**

### Test RLS Before Sharing

Security should be tested using actual user scenarios.

Example:

**North User**

```text
North = Visible
South = Not Visible
```

**South User**

```text
South = Visible
North = Not Visible
```

**Unknown User**

Behavior should match the intended security design.

### Important Rule

> **Never assume security works simply because the DAX expression contains no syntax error. Test the actual user scenarios.**

## 11.17 Static RLS

**Static RLS uses predefined roles with fixed filter conditions.**

Example role:

```text
North Manager
```

Filter:

```DAX
DimRegion[Region] = "North"
```

Another role:

```text
South Manager
```

Filter:

```DAX
DimRegion[Region] = "South"
```

### Conceptual Flow

```text
Role: North
     ↓
Region = North
     ↓
North Users
     ↓
North Data
```

### Static RLS Example

Suppose there are four regional managers.

We could create:

**North**

```DAX
DimRegion[Region] = "North"
```

**South**

```DAX
DimRegion[Region] = "South"
```

**East**

```DAX
DimRegion[Region] = "East"
```

**West**

```DAX
DimRegion[Region] = "West"
```

Users are then assigned to the corresponding role.

### Simple Understanding

> **Static RLS = Fixed security rule defined for a role**

### Limitation

If the organization has:

```text
500 Managers
```

creating and maintaining a large number of separate fixed roles can become difficult.

This is where Dynamic RLS may become more scalable.

---

## 11.18 Dynamic RLS

**Dynamic RLS determines allowed data based on the identity of the person currently viewing the report.**

Instead of creating a separate fixed role for every user, we can use a security mapping table.

Example:

| UserEmail | Region |
|---|---|
| north.manager@company.com | North |
| south.manager@company.com | South |
| west.manager@company.com | West |

The logged-in user's identity is matched against this table.

### Conceptual Architecture

```text
User
  ↓
UserAccess
  ↓
Allowed Region
  ↓
DimRegion
  ↓
FactSales
  ↓
Report
```

### Example UserAccess Table

| Email | Region |
|---|---|
| a@company.com | North |
| b@company.com | South |
| c@company.com | East |

The model can work conceptually like:

```text
UserAccess
    |
    |
DimRegion
    |
    |
FactSales
```

### Why Dynamic RLS Can Be Useful

It can be more scalable when:

- Many users exist
- Access differs by Region
- Access differs by Business Unit
- Access differs by Customer
- Access needs to be controlled through a mapping table

### Simple Understanding

> **Dynamic RLS = User Identity Determines Allowed Data**

---

## 11.19 `USERPRINCIPALNAME()`

A commonly used DAX function for Dynamic RLS is:

```DAX
USERPRINCIPALNAME()
```

It can return the identity of the current user in an email/UPN-style format in supported Power BI scenarios.

### Example

Logged-in user:

```text
north.manager@company.com
```

Then:

```text
USERPRINCIPALNAME()
        ↓
north.manager@company.com
        ↓
Match UserAccess Table
        ↓
Region = North
        ↓
North Data Only
```

### Conceptual Dynamic RLS Logic

```text
Current User
     ↓
USERPRINCIPALNAME()
     ↓
Security Mapping Table
     ↓
Allowed Dimension Value
     ↓
Fact Table
     ↓
Report
```

### Important

The user identity should match the values maintained in the security mapping table.

If the mapping is incorrect or missing, the resulting security behavior may not match the intended design.

---

## 11.20 Static vs Dynamic RLS

Static and Dynamic RLS solve the same general security requirement using different approaches.

| Static RLS | Dynamic RLS |
|---|---|
| Fixed filter for each role | Filter based on current user identity |
| May require multiple roles | Can often use a common role |
| Simple for a few groups | More scalable for many users |
| Example: Region = North | Example: Email = current user |
| More manual role maintenance | Uses user/security mapping |

### Easy Way to Remember

> **Static RLS = Role Determines Data**

> **Dynamic RLS = User Identity Determines Data**

### When Static RLS May Be Suitable

Example:

```text
4 Regions
4 Fixed User Groups
```

Static roles may be simple enough.

### When Dynamic RLS May Be Suitable

Example:

```text
Hundreds of Managers
Multiple Regions
Changing User Assignments
```

A centralized security mapping table may be easier to maintain.

### Important

The correct choice depends on the actual security requirement.

## 11.21 Power BI Apps

After report development, validation and security testing, content can be distributed to users.

A **Power BI App packages related Power BI content into a curated consumption experience.**

An App can provide:

- Curated content
- Centralized distribution
- Audience management
- Cleaner navigation
- Multiple related reports
- Separation between development and consumption

### Simple Understanding

> **Workspace = Development / Collaboration**

> **App = Curated Business Consumption**

### Report Publishing

A typical flow is:

```text
Develop Report
      ↓
Validate
      ↓
Apply Security
      ↓
Publish
      ↓
Power BI Service
      ↓
Power BI App
      ↓
Business Users
```

### Why App Presentation Matters

For a complete analytics solution, showing only a report-development screen does not demonstrate the entire consumption experience.

A more complete flow is:

```text
Pipeline
   ↓
Lakehouse
   ↓
Warehouse / Model
   ↓
Power BI Report
   ↓
Power BI App
   ↓
Business User
```

### Interactive Report vs PDF Snapshot

An interactive Power BI report can provide:

- Slicer interaction
- Cross-filtering
- Drill-down
- Dynamic titles
- Security-aware viewing

A PDF export represents a snapshot at a particular point or filter context.

Therefore:

> **Interactive Report = Analytical Experience**

> **PDF = Static Snapshot**

## 11.22 Workspace vs Power BI App

Workspace and Power BI App have different purposes.

| Workspace | Power BI App |
|---|---|
| Used for development and collaboration | Used for curated distribution |
| Contains development artifacts | Presents selected content |
| Engineers / Analysts may work here | Business users primarily consume here |
| Can contain working items | Can expose finalized content |
| Workspace permissions apply | App audience/access can be configured |

### Simple Understanding

> **Workspace = Create and Collaborate**

> **App = Distribute and Consume**

### Practical Understanding

Business users should not necessarily need to browse the entire development workspace simply to consume a finalized report.

A Power BI App can provide a cleaner end-user experience.

### Example

```text
Development Team
       ↓
Workspace
       ↓
Reports + Models + Other Items
       ↓
Power BI App
       ↓
Selected Final Content
       ↓
Business Users
```

## 11.23 Direct Lake

In Fabric, a Power BI Semantic Model can use **Direct Lake** to work with Delta data stored in OneLake.

Conceptually:

```text
Delta Tables in OneLake
          ↓
      Direct Lake
          ↓
    Semantic Model
          ↓
    Power BI Report
```

The report still interacts through the Semantic Model.

The Semantic Model provides:

- Tables
- Relationships
- Measures
- Business logic
- Security

while Direct Lake provides the connection between Fabric data in OneLake and the analytical model.

### Gold / Star Schema and Reporting

The report should ideally consume clean and properly modelled business data.

A poor model can lead to:

- Complex DAX
- Difficult relationships
- Poor performance
- Confusing report behavior

A useful architecture is:

```text
Bronze
Raw
  ↓
Silver
Clean
  ↓
Gold
Business-Ready
  ↓
Star Schema
Fact + Dimensions
  ↓
Semantic Model
Measures + Relationships + Security
  ↓
Power BI Report
```

### Important Understanding

Reporting quality depends strongly on the upstream model.

> **Good reporting starts before Power BI visuals are created.**

## 11.24 Interview Understanding

### What is the Role of Power BI in a Fabric Solution?

Power BI acts as the analytical visualization and consumption layer.

It allows business users to interact with:

- Measures
- Dimensions
- Filters
- Visuals
- Reports

through a Semantic Model.

### What is the Difference Between Report and Semantic Model?

> **Semantic Model = Analytical structure and logic**

> **Report = Visual presentation and interaction**

### Why Should Report Building Start With Business Questions?

Because visuals should be selected to answer specific business questions rather than added randomly.

A useful process is:

> **Business Question → Measure → Visual**

### What is the Difference Between Measure and Calculated Column?

> **Calculated Column = Row-level stored calculation**

> **Measure = Dynamic calculation based on Filter Context**

### What is Filter Context?

Filter Context is the set of filters affecting a Measure when it is evaluated.

It can come from:

- Slicers
- Dimensions
- Visual interactions
- Report filters

### Why Are Dimensions Important?

Dimensions provide the context used to:

- Filter
- Group
- Slice

Fact measurements.

### What is RLS?

Row-Level Security restricts which rows of data a user can access through the Semantic Model.

### What is Static RLS?

Static RLS uses fixed role-based filters.

Example:

```DAX
DimRegion[Region] = "North"
```

### What is Dynamic RLS?

Dynamic RLS determines allowed data based on the identity of the current user.

### Static RLS vs Dynamic RLS?

> **Static RLS = Fixed Role Filter**

> **Dynamic RLS = User Identity-Based Filter**

### Why Can Dynamic RLS Be Better for Many Users?

Because instead of creating many separate fixed roles, a centralized user-access table can map each user to the data they are allowed to access.

### What Does `USERPRINCIPALNAME()` Do?

It can return the current user's identity in an email/UPN-style form in supported Power BI scenarios and can be used as part of Dynamic RLS logic.

### Is Hiding a Visual a Security Method?

No.

Hiding a visual does not provide row-level data security.

Security should be implemented at the appropriate model/data level.

### What is a Power BI App?

A Power BI App is a curated way to package and distribute Power BI content to business users.

### Workspace vs App?

> **Workspace = Create and Collaborate**

> **App = Distribute and Consume**

### What is Direct Lake?

Direct Lake is a Fabric reporting approach in which the Semantic Model can work with Delta data stored in OneLake.

### Why Validate the Report?

Because a report can execute successfully and still contain incorrect business results.

Report KPIs should reconcile with the underlying validated data.

### Real-World Reporting Mindset

A beginner may think:

> **My job is finished when the chart looks good.**

A stronger practical mindset is:

> **The report must contain correct data, a proper model, understandable KPIs, useful interactions, appropriate security, good performance and a suitable distribution method.**

A professional report should therefore consider:

```text
Accuracy
    +
Usability
    +
Performance
    +
Security
    +
Distribution
```
