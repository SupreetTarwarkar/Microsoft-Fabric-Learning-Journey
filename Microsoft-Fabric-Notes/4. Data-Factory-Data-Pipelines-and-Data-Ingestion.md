# Chapter 4: Data Factory, Data Pipelines and Data Ingestion

---

## 4.1 Data Factory in Microsoft Fabric

**Data Factory is the data integration and orchestration capability within Microsoft Fabric.**

It is used to:

- Connect to different data sources
- Move data
- Integrate data
- Transform data
- Automate data workflows
- Orchestrate different data-processing activities

A simple way to remember:

> **Data Factory helps bring data into Fabric and orchestrate what should happen to that data.**

### Simple Flow

```text
Source System
      ↓
Data Factory
      ↓
Lakehouse / Warehouse
```

Data Factory becomes especially important when data needs to be moved repeatedly and automatically instead of manually uploading files every day.

---

## 4.2 Data Ingestion

**Data ingestion means bringing data from one or more source systems into the analytics platform.**

Possible sources include:

- SQL Server
- Azure SQL Database
- CSV
- Excel
- APIs
- Cloud storage
- On-premises databases
- Business applications
- Other supported data sources

### Example

Suppose a company generates a new sales file every day.

Instead of manually downloading and uploading the file:

```text
Sales Source
     ↓
Fabric Data Pipeline
     ↓
Lakehouse
```

The process can be automated.

Therefore:

> **Ingestion = Getting data from the source into the required destination.**

### Manual vs Automated Data Processing

**Manual process:**

```text
Download File
      ↓
Upload File
      ↓
Run Transformation
      ↓
Load Table
      ↓
Refresh Report
```

Someone has to repeat these steps regularly.

**Automated process:**

```text
Scheduled Pipeline
      ↓
Copy
      ↓
Transform
      ↓
Load
      ↓
Downstream Processing
```

Automation reduces manual intervention and makes repeatable data processes easier to manage.

## 4.3 Data Pipelines

A **Data Pipeline is an orchestration mechanism used to create and automate a sequence of data-related activities.**

A pipeline tells Fabric:

- What activity should run
- In what sequence activities should run
- Where the data should come from
- Where the data should go
- What should happen after an activity succeeds
- What should happen after an activity fails

### Simple Example

```text
Copy Sales Data
      ↓
Run Notebook
      ↓
Transform Data
      ↓
Load Warehouse
      ↓
Refresh Downstream Process
```

Instead of manually performing these steps every day, the pipeline can orchestrate them.

### Easy Definition

> **Pipeline = A workflow that coordinates and automates data activities.**

### Practical End-to-End Pipeline

A realistic Fabric data workflow could look like:

```text
SQL / CSV / API
      ↓
Copy Activity
      ↓
Bronze Layer
      ↓
Notebook Activity
      ↓
Silver Layer
      ↓
Notebook / SQL / Dataflow Gen2
      ↓
Gold Layer
      ↓
Warehouse / Semantic Model
      ↓
Power BI
```

The **Pipeline orchestrates the complete sequence**.

### Real-World Understanding

The important learning is not simply:

> **I know how to drag a Copy activity into a pipeline.**

A stronger understanding is:

> **Pipelines are used to orchestrate repeatable data workflows. They can ingest data from source systems, execute transformations through Notebooks or Dataflow Gen2, control dependencies, use parameters for reusability, schedule execution, and provide monitoring for production data processes.**

---

## 4.4 Data Movement vs Orchestration

These two concepts should not be confused.

### Data Movement

Data movement means actually transferring data:

```text
Source → Destination
```

Example:

```text
CSV → Lakehouse
```

### Orchestration

Orchestration means managing the complete workflow.

For example:

```text
Copy Data
    ↓
Run Notebook
    ↓
Execute Another Process
    ↓
Send Notification
```

Therefore:

> **Data Movement = Move the data**

> **Orchestration = Control the workflow**

A Fabric Pipeline can be involved in both.

---

## 4.5 Pipeline Activities

A Pipeline consists of **activities**.

An activity represents a particular task that should be performed.

Some important Fabric Pipeline activities include:

| Activity | Purpose |
|---|---|
| **Copy Data** | Move data from source to destination |
| **Notebook** | Execute a Fabric Notebook |
| **Dataflow Gen2** | Execute a Dataflow Gen2 |
| **Stored Procedure** | Execute a stored procedure |
| **Script** | Execute SQL/script operations |
| **Lookup** | Retrieve data or a value for later use |
| **ForEach** | Repeat activities for multiple items |
| **If Condition** | Execute activities based on a condition |
| **Set Variable** | Store or change a pipeline variable |
| **Wait** | Pause execution for a specified period |

I do not need to memorize every available Pipeline activity.

The important thing is understanding:

> **Which activity solves which type of problem?**

### Why Activity Naming Matters

Names such as:

```text
Copy1
Notebook1
```

may be acceptable while learning, but they are poor names for production workflows.

Better examples:

```text
CopyRawSalesData

TransformBronzeToSilver

BuildGoldSales

LoadSalesWarehouse
```

Descriptive names make troubleshooting much easier.

> **Descriptive Naming → Faster Troubleshooting and Debugging**

## 4.6 Copy Data Activity

**Copy Data is one of the most important Pipeline activities.**

Its main purpose is:

> **Move data from a source to a destination.**

### Example 1

```text
SQL Server
     ↓
Copy Data Activity
     ↓
Fabric Lakehouse
```

### Example 2

```text
CSV
 ↓
Copy Data
 ↓
Delta Table
```

Copy Activity mainly deals with **data movement** rather than complex business transformations.

### Basic Copy Data Process

```text
Create Pipeline
      ↓
Add Copy Data Activity
      ↓
Configure Source
      ↓
Configure Destination
      ↓
Configure Mapping
      ↓
Run Pipeline
      ↓
Validate Destination Data
```

---

## 4.7 Source and Destination

A Copy Data activity generally needs two important components:

### Source

The **Source** identifies where the data currently exists.

Examples:

- SQL database
- CSV file
- Cloud storage
- Another supported system

### Destination

The **Destination** identifies where the data should be copied.

Examples:

- Lakehouse
- Warehouse
- Supported OneLake destinations

### Simple Flow

```text
SOURCE
Where is my data?
      ↓
COPY ACTIVITY
Move the data
      ↓
DESTINATION
Where should my data go?
```

### Auto-Create Destination Table

Fabric can support scenarios where a destination table is automatically created based on the incoming source structure.

This can be convenient for:

- Learning
- Initial ingestion
- Raw or staging layers
- Quick development

However, this should **not automatically be considered the best production approach for every table**.

For important production tables, we may want to explicitly control:

- Column names
- Data types
- Table structure
- Naming standards
- Governance rules

A useful rule is:

> **Auto-create is convenient, but important production schemas should be deliberately designed when more control is required.**

## 4.8 Connections

To access an external data source, Fabric needs information about how to connect to that system.

A **Connection** contains the information required to connect to a source or destination.

Depending on the source, this may involve:

- Server
- Database
- Authentication
- Credentials
- Connection configuration

### Simple Understanding

> **Connection = How Fabric connects to the source or destination system.**

The Pipeline then uses that connection when accessing the data.

### Basic Relationship

```text
Source System
      ↓
Connection
      ↓
Pipeline Activity
      ↓
Destination
```

## 4.9 Column Mapping

Sometimes the source column names or structures do not exactly match the destination.

**Column Mapping** tells the Pipeline which source column should populate which destination column.

Example:

| Source | Destination |
|---|---|
| `Order_ID` | `OrderID` |
| `Order_Date` | `OrderDate` |
| `Sales_Amount` | `Revenue` |

Therefore:

> **Mapping connects source fields with their corresponding destination fields.**

Mapping becomes especially important when source and destination schemas differ.

### Copy Flow Including Mapping

```text
Source
   ↓
Connection
   ↓
Copy Data Activity
   ↓
Column Mapping
   ↓
Destination
   ↓
Validate Data
```

## 4.10 Pipeline Dependencies

Pipeline activities do not always run independently.

We can define what should happen based on the result of a previous activity.

Conceptually:

```text
Activity A
    ↓
Success
    ↓
Activity B
```

### Example

```text
Copy Raw Data
      ↓
Success
      ↓
Run Transformation Notebook
      ↓
Success
      ↓
Load Business-Ready Data
```

If the Copy operation fails, we normally do not want transformation logic to continue using incomplete data.

Dependencies help ensure that activities execute in the correct order.

---

## 4.11 Sequential vs Parallel Execution

Pipeline activities can execute either **sequentially** or **in parallel**, depending on dependencies.

### Sequential Execution

One activity depends on another.

```text
A → B → C
```

Example:

```text
Copy → Transform → Load
```

### Parallel Execution

Independent activities can execute at the same time.

```text
          → Copy Customers
Start     → Copy Products
          → Copy Sales
```

Parallel execution can reduce total processing time when activities do not depend on each other.

### Important

> **Do not make activities parallel simply because parallel execution is faster.**

Activities should only run in parallel when no required dependency exists between them.

## 4.12 Parameters

A **Parameter allows a Pipeline to become more dynamic and reusable.**

Without parameters, values may be hard-coded.

Example:

```text
Sales_2026_08_16.csv
```

Tomorrow:

```text
Sales_2026_08_17.csv
```

Instead of creating a new Pipeline every day, we can use a parameter.

```text
FileName = Parameter
```

The same Pipeline can then process different files depending on the supplied value.

### Why Parameters Matter

Parameters make Pipelines:

- Dynamic
- Reusable
- Maintainable
- Suitable for different files
- Suitable for different tables
- Suitable for different environments

### Simple Understanding

> **Hard-Coded Pipeline = Built for one fixed situation**

> **Parameterized Pipeline = Same Pipeline can work with changing inputs**

Common parameter examples include:

```text
FileName
TableName
FolderPath
LoadDate
Environment
```

---

## 4.13 Variables vs Parameters

Parameters and Variables are related, but they are different.

### Parameter

A Parameter normally receives an input value used during Pipeline execution.

Examples:

```text
FileName
TableName
LoadDate
```

### Variable

A Variable can hold or change a value while the Pipeline is running.

### Simple Difference

> **Parameter = Input to the Pipeline**

> **Variable = Value used or changed during Pipeline execution**

## 4.14 Lookup Activity

**Lookup Activity** is useful when we need to retrieve information and use it later in the Pipeline.

Suppose we maintain a control table:

| TableName | LoadFlag |
|---|---|
| Sales | Yes |
| Customer | Yes |
| Product | No |

A Lookup Activity can read this configuration.

The Pipeline can then decide what should be processed.

### Example

```text
Control Table
      ↓
Lookup Activity
      ↓
Read Configuration
      ↓
Pipeline Decision
```

This is more scalable than hard-coding every processing decision inside the Pipeline.

---

## 4.15 ForEach Activity

**ForEach** allows a Pipeline to repeat an activity for multiple items.

Suppose I need to load:

- Sales
- Customers
- Products
- Stores

Instead of creating four nearly identical Pipelines:

```text
List of Tables
      ↓
ForEach
      ↓
Copy Current Table
```

The same logic can be reused for each table.

### Why ForEach is Important

ForEach is an important step toward building:

- Reusable Pipelines
- Dynamic Pipelines
- Metadata-driven Pipelines

---

## 4.16 If Condition

An **If Condition** allows different actions depending on whether a condition evaluates to true or false.

### Example 1

```text
Has New File Arrived?
      ↓
YES → Process File
NO  → Skip Processing
```

### Example 2

```text
Row Count > 0?
      ↓
YES → Continue
NO  → Stop / Handle Condition
```

This helps Pipelines react dynamically rather than executing every step blindly.

---

## 4.17 Notebook Activity

A Pipeline can execute a Fabric Notebook.

This is important because Pipelines and Notebooks have different responsibilities.

### Pipeline

Primarily handles:

- Orchestration
- Data movement
- Dependencies
- Scheduling
- Workflow control

### Notebook

Primarily handles:

- Data transformation
- PySpark
- Complex processing
- Data engineering logic

### Example

```text
Pipeline
   ↓
Copy Source Data into Bronze
   ↓
Notebook Activity
   ↓
Clean and Transform
   ↓
Bronze → Silver
```

Therefore:

> **Pipeline orchestrates the process; Notebook performs transformation logic.**

---

## 4.18 Dataflow Gen2 Activity

A Pipeline can also execute **Dataflow Gen2** as part of the workflow.

This allows Power Query-based transformations to become part of an automated Fabric process.

Conceptually:

```text
Copy Data
    ↓
Dataflow Gen2
    ↓
Notebook
    ↓
Warehouse
```

### Pipeline vs Notebook vs Dataflow Gen2

| Tool | Simple Understanding |
|---|---|
| **Pipeline** | Orchestration and data movement |
| **Notebook** | Code/PySpark-based transformation |
| **Dataflow Gen2** | Low-code Power Query-based transformation |

### When Might I Use Each?

If I only need to move data:

> **Pipeline / Copy Activity**

If I need large-scale PySpark transformations:

> **Notebook**

If Power Query is suitable for the transformation:

> **Dataflow Gen2**

These tools can also work **together** rather than always competing with one another.

A useful division of responsibility is:

> **Pipeline = Orchestration**

> **Notebook = Code/PySpark Transformation**

> **Dataflow Gen2 = Power Query/Low-Code Transformation**

## 4.19 Scheduling a Pipeline

A Pipeline becomes much more useful when it runs automatically.

### Business Requirement Example

Every day at **6:00 AM**:

1. Load sales data
2. Transform the data
3. Prepare reporting tables
4. Make updated data available for reporting

Instead of manually running the Pipeline every morning, the workflow can be scheduled.

### Conceptual Flow

```text
Schedule
    ↓
Pipeline Starts
    ↓
Ingest
    ↓
Transform
    ↓
Load
    ↓
Reporting Data Updated
```

This is a basic example of **workflow automation**.

### Why Scheduling Matters

Scheduling helps:

- Reduce manual work
- Ensure repeatable execution
- Keep data updated
- Support recurring business processes
- Make analytics workflows more reliable

## 4.20 Pipeline Monitoring

After running a Pipeline, we should not simply assume it succeeded.

We should be able to check:

- Pipeline status
- Activity status
- Start time
- End time
- Duration
- Failed activity
- Error details

Possible statuses may include:

- Succeeded
- Failed
- Running
- Cancelled

Monitoring becomes especially important in production.

### Basic Error Handling Understanding

Pipelines can fail for many reasons.

Examples:

- Source file missing
- Invalid credentials
- Connection failure
- Incorrect file path
- Schema mismatch
- Incorrect data type
- Destination unavailable
- Timeout
- Capacity/resource issue
- Notebook failure

Therefore, production Pipelines should not be designed with the assumption:

> **It worked once, so it will always work.**

A practical production Pipeline should eventually include:

> **Monitoring + Error Handling + Alerting**

### Why Descriptive Names Help Monitoring

Compare:

```text
Notebook1
```

with:

```text
TransformBronzeToSilver
```

If a Pipeline fails, the second name immediately provides more context.

Therefore:

> **Clear naming makes monitoring and troubleshooting easier.**

Detailed concepts such as:

- Monitoring Hub
- Duration analysis
- Alerts
- Debugging
- Root-cause analysis

are covered later in the dedicated Monitoring chapter.

## 4.21 Interview Understanding

### What is Data Factory in Microsoft Fabric?

Data Factory is Microsoft Fabric's data integration and orchestration capability.

It helps connect to data sources, ingest data, move data, automate workflows and coordinate different data-processing activities.

### What is Data Ingestion?

> **Data ingestion means bringing data from source systems into the analytics platform for storage, processing and analysis.**

### What is a Data Pipeline?

A Data Pipeline is an orchestration workflow used to automate data movement and other data-processing activities.

It can coordinate activities such as:

- Copy Data
- Notebook execution
- Dataflow Gen2
- Stored procedures
- Conditional activities
- Other supported operations

### What is Copy Activity?

Copy Activity is primarily used to move data from a source system to a destination.

Example:

```text
SQL Server → Copy Activity → Fabric Lakehouse
```

### What is the difference between Data Movement and Orchestration?

> **Data Movement moves the data, while Orchestration coordinates and controls the complete workflow.**

### What is the difference between a Pipeline and a Notebook?

> **A Pipeline primarily orchestrates the workflow, while a Notebook performs code-based data processing and transformations.**

A Pipeline can execute a Notebook as one of its activities.

### Why do we use Parameters?

Parameters make Pipelines dynamic and reusable by allowing changing values such as:

- File name
- Table name
- Folder path
- Load date

to be supplied instead of hard-coded.

### What is the difference between a Parameter and Variable?

> **A Parameter is generally an input supplied to a Pipeline, while a Variable holds a value that can be used or changed during execution.**

### Why use ForEach?

ForEach allows the same set of activities to be repeated for multiple items.

For example, the same Copy logic could load multiple tables instead of creating a separate Pipeline for every table.

### What is Orchestration?

> **Orchestration means coordinating the order, dependencies and execution of different activities in a data workflow.**

### Why is Pipeline Monitoring Important?

Pipeline monitoring helps us identify:

- Failed runs
- Failed activities
- Long-running activities
- Error details
- Performance issues
- Potential production problems
