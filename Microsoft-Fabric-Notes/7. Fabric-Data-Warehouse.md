# Chapter 7: Fabric Data Warehouse

---

## 7.1 What is a Data Warehouse?

A **Data Warehouse is a centralized analytical data store designed for structured data, SQL-based analysis, reporting and business intelligence.**

In Microsoft Fabric, a Warehouse provides a relational data warehousing experience where we can work primarily using **T-SQL**.

A simple way to remember:

> **Lakehouse = Flexible engineering-oriented environment**

> **Warehouse = Structured SQL-first analytical environment**

A Fabric Warehouse is useful when the solution requires:

- Structured analytical data
- SQL-based analytics
- Relational tables
- Schemas
- Views
- Stored procedures
- Fact and dimension tables
- Power BI reporting

### Why Do We Need a Data Warehouse?

After raw data has been ingested and transformed, business users generally do not want to work directly with raw files.

They need structured analytical data.

A possible flow is:

```text
Raw Sales Files
       ↓
Bronze
       ↓
Silver
       ↓
Gold / Business-Ready Data
       ↓
Warehouse
       ↓
Power BI
```

The Warehouse provides a structured SQL environment for serving analytical data.

## 7.2 Fabric Warehouse

**Microsoft Fabric Warehouse is a SQL-based analytical data warehouse built into Microsoft Fabric.**

It provides capabilities such as:

- Tables
- Schemas
- Views
- Stored procedures
- T-SQL querying
- Relational modelling
- Power BI integration

Users interact with the Warehouse primarily through a familiar relational SQL experience.

### Simple Understanding

```text
Fabric
   ↓
Warehouse
   ↓
Structured Relational Data
   ↓
SQL Analytics
   ↓
Power BI
```

The Warehouse participates in the wider Fabric data platform and OneLake architecture.

---

## 7.3 Warehouse as a SQL-First Experience

One of the main reasons to use a Warehouse is when the workload or team is strongly SQL-oriented.

For example:

```sql
SELECT
    ProductCategory,
    SUM(Revenue) AS TotalRevenue
FROM fact_sales
GROUP BY ProductCategory;
```

For SQL developers, analysts and BI professionals, this provides a familiar way to work with analytical data.

### Simple Understanding

> **Warehouse = Structured analytical data + SQL-first experience**

### SQL Aggregations in a Warehouse

Warehouse data can be analyzed using familiar SQL operations.

Example:

```sql
SELECT
    ProductCategory,
    SUM(Revenue) AS TotalRevenue,
    COUNT(*) AS TotalOrders
FROM sales.fact_sales
GROUP BY ProductCategory
ORDER BY TotalRevenue DESC;
```

This can answer business questions such as:

- Revenue by product category
- Number of orders
- Highest-performing category

SQL therefore becomes an important analytical interface for Fabric Warehouse data.

## 7.4 Tables in a Warehouse

A Fabric Warehouse contains relational tables.

For example:

### Fact Table

```text
fact_sales
```

### Dimension Tables

```text
dim_customer
dim_product
dim_date
dim_region
```

These tables can later participate in a dimensional analytical model.

Conceptually:

```text
             dim_product
                  |
                  |
dim_customer — fact_sales — dim_date
                  |
                  |
              dim_region
```

This type of structure is commonly known as a **Star Schema**.

Star Schema and detailed data modelling are covered separately later.

### Why Relational Tables Matter

Structured Warehouse tables make it easier to perform:

- SQL queries
- Joins
- Aggregations
- Dimensional modelling
- Business reporting
- Power BI analysis

## 7.5 Schemas

A **Schema is a logical container or namespace used to organize database objects such as tables and views inside a Warehouse.**

Instead of placing every object together:

```text
fact_sales
dim_customer
employee
department
```

we can organize objects logically.

Example:

```text
sales.fact_sales
sales.dim_customer

hr.employee
hr.department
```

Here:

```text
sales = Schema
fact_sales = Table
```

### Simple Understanding

> **Warehouse → Schema → Tables / Views / Other Objects**

### Creating Schemas

Schemas can be created using T-SQL.

Example:

```sql
CREATE SCHEMA sales;
```

Then objects can be created inside the schema.

Example:

```sql
CREATE TABLE sales.fact_sales
(
    OrderID INT,
    ProductID INT,
    Revenue DECIMAL(18,2)
);
```

### Important

Schemas should be created according to the organization's data architecture.

We should not create unnecessary schemas simply because the capability exists.

---

## 7.6 Why Use Schemas?

Schemas help organize Warehouse objects logically.

Benefits include:

- Organization
- Naming
- Security
- Object management
- Separation of business areas
- Easier maintenance

### Example — Sales Schema

```text
sales.fact_sales
sales.dim_product
```

### Finance Schema

```text
finance.fact_budget
finance.dim_account
```

### HR Schema

```text
hr.fact_employee
hr.dim_department
```

This is cleaner than placing hundreds of unrelated database objects together.

### Easy Way to Remember

> **Schema = Logical organization of Warehouse objects**

Schemas can also make it easier to identify which business domain an object belongs to.

## 7.7 When to Use a Fabric Warehouse

A Fabric Warehouse becomes a strong option when the solution has characteristics such as:

### Structured Relational Data

The data naturally fits into:

- Tables
- Rows
- Columns
- Relationships

### SQL-First Workloads

The team primarily uses SQL for:

- Querying
- Analytics
- Transformation
- Data serving

### Analytical / BI Requirement

The data is being prepared for:

- Reporting
- Semantic models
- Business analytics
- Dimensional modelling

### Simple Rule

> **If the workload is structured, relational, analytical and SQL-centric, Fabric Warehouse becomes a strong option.**

This is better than saying:

> **Warehouse is always better than Lakehouse.**

The correct choice depends on the use case.

---

## 7.8 Lakehouse vs Warehouse

This is one of the most important Microsoft Fabric comparisons.

| Lakehouse | Warehouse |
|---|---|
| Flexible data architecture | Structured relational architecture |
| Strong data engineering use cases | Strong SQL and BI use cases |
| Supports files and tables | Primarily relational tables |
| Spark / PySpark friendly | T-SQL friendly |
| Useful for raw and transformed data | Useful for curated analytical data |
| Commonly used by Data Engineers | Commonly useful for SQL / BI teams |
| Supports structured and file-based scenarios | Primarily structured relational data |
| Strong for Bronze / Silver engineering | Strong for structured analytical serving |

### Important

This does **not** mean:

```text
Lakehouse = Data Engineer only
```

or:

```text
Warehouse = Data Analyst only
```

Both can participate in broader Fabric solutions.

The comparison represents their **typical strengths**, not strict user restrictions.

### Simple Difference

> **Lakehouse = Flexible engineering + Spark + Files + Delta**

> **Warehouse = Structured analytics + Relational SQL**

---

## 7.9 Lakehouse and Warehouse Together

Lakehouse and Warehouse are not necessarily competitors.

A Fabric solution can use both.

Example:

```text
Source
   ↓
Pipeline
   ↓
Lakehouse Bronze
Raw Data
   ↓
Lakehouse Silver
Cleaned Data
   ↓
Gold / Business-Ready Data
   ↓
Fabric Warehouse
Fact + Dimension Tables
   ↓
Power BI
```

This allows Data Engineers to use flexible engineering tools upstream while SQL and BI users consume structured relational data downstream.

### Do I Always Need Both?

No.

A project does **not automatically require both a Lakehouse and Warehouse**.

#### Scenario 1

If the complete solution works effectively using:

```text
Lakehouse
   +
Delta Tables
   +
Power BI
```

then adding a Warehouse simply because it exists may create unnecessary complexity.

#### Scenario 2

If the organization requires:

- Strong SQL development
- Schemas
- Relational analytical objects
- Stored procedures
- SQL-based analytical serving

then Warehouse may add value.

### Practical Principle

> **Choose architecture according to requirements, not according to how many Fabric tools are available.**

### Lakehouse and Warehouse in OneLake Architecture

Both Lakehouse and Warehouse participate in the broader Fabric and OneLake architecture.

Conceptually:

```text
             OneLake
             /     \
            /       \
     Lakehouse     Warehouse
        ↓             ↓
Engineering      SQL Analytics
Experience        Experience
```

They provide different analytical experiences within the broader Fabric ecosystem.

## 7.10 Views

A **View is a saved SQL query that presents data like a virtual table.**

Suppose a table contains:

```text
OrderID
CustomerID
ProductID
Revenue
Status
```

We only want completed sales.

Instead of repeatedly writing:

```sql
SELECT *
FROM sales.fact_sales
WHERE Status = 'Completed';
```

we can create a View:

```sql
CREATE VIEW sales.vw_completed_sales
AS
SELECT *
FROM sales.fact_sales
WHERE Status = 'Completed';
```

Then query it:

```sql
SELECT *
FROM sales.vw_completed_sales;
```

### Simple Understanding

> **View = Saved query / virtual representation of data**

### Why Use Views?

Views can help with:

- Simplifying complex queries
- Reusing query logic
- Presenting selected columns
- Abstracting underlying tables
- Creating business-friendly datasets
- Improving maintainability

For example, instead of repeatedly exposing a complex combination of:

```text
fact_sales
     +
dim_product
     +
dim_customer
     +
dim_region
```

we can expose a simpler analytical View.

### Does a Normal View Store Another Copy of the Data?

Normally, a standard SQL View stores the **query definition**, not a separate physical copy of all the result data.

When the View is queried, the underlying tables are accessed.

Therefore:

> **Table stores data.**

> **View normally stores query logic.**

This is an important interview distinction.

## 7.11 Stored Procedures

A **Stored Procedure is reusable executable SQL logic stored inside the database or Warehouse.**

A Stored Procedure can contain multiple SQL statements and perform actions.

Example:

```sql
CREATE PROCEDURE sales.usp_load_sales
AS
BEGIN

    INSERT INTO sales.fact_sales
    SELECT *
    FROM sales.staging_sales;

END;
```

The procedure can then be executed whenever required.

### Simple Understanding

> **Stored Procedure = Stored reusable SQL program / action**

### Why Stored Procedures are Useful

Stored Procedures can help when the same SQL processing needs to run repeatedly.

Examples include:

- Loading analytical tables
- Performing repeatable transformations
- Executing business logic
- Data maintenance operations
- Supporting Pipeline-controlled SQL processing

Benefits include:

- Reusability
- Maintainability
- Standardization

### Pipeline + Stored Procedure

Stored Procedures can also participate in an orchestrated Fabric workflow.

Example:

```text
Pipeline
   ↓
Copy Data
   ↓
Run Notebook
   ↓
Load Silver
   ↓
Execute Stored Procedure
   ↓
Populate Warehouse Table
   ↓
Power BI
```

This demonstrates an important Fabric concept:

> **Different Fabric components can work together as part of one data solution.**

---

## 7.12 View vs Stored Procedure

Views and Stored Procedures solve different problems.

| View | Stored Procedure |
|---|---|
| Saved query | Stored executable SQL logic |
| Mainly used to present/query data | Used to perform reusable actions or processes |
| Queried like a table | Explicitly executed |
| Generally provides a relational result | Can contain multiple SQL statements |
| Useful for abstraction and read scenarios | Useful for processing logic |

### Easy Way to Remember

> **View = See / Query Data**

> **Stored Procedure = Do / Execute Something**

This is a simplified distinction, but it is useful for remembering the fundamental difference.

## 7.13 Fact Tables

A **Fact Table contains measurable business events or transactions.**

Examples include:

- Sales
- Orders
- Payments
- Bookings

A Sales Fact table might contain:

| DateKey | ProductKey | CustomerKey | Quantity | Revenue |
|---:|---:|---:|---:|---:|
| 20260816 | 101 | 5001 | 2 | 70000 |

Typical numeric measures include:

- Revenue
- Quantity
- Cost
- Discount

### Simple Understanding

> **Fact Table = Business event + measurable values**

For example:

```text
Sales Transaction
        ↓
Quantity
Revenue
Cost
Discount
```

Fact tables are generally analyzed using descriptive information from Dimension tables.

---

## 7.14 Dimension Tables

A **Dimension Table contains descriptive information used to analyze Fact data.**

Examples include:

### Product Dimension

```text
dim_product
```

May contain:

- ProductKey
- ProductName
- Category

### Customer Dimension

```text
dim_customer
```

May contain:

- CustomerKey
- CustomerName
- City

### Date Dimension

```text
dim_date
```

May contain:

- DateKey
- Date
- Month
- Quarter
- Year

Fact and Dimension tables can eventually form the analytical data model used by Power BI.

### Simple Understanding

> **Fact = What happened?**

> **Dimension = How do I describe or analyze what happened?**

Example:

```text
Fact Sales
   ↓
Revenue = 50,000

Dimensions
   ↓
Which Product?
Which Customer?
Which Date?
Which Region?
```

If a Warehouse contains well-designed:

- Fact tables
- Dimension tables
- Relationships
- Business-ready structures

Power BI can consume that data for:

- Semantic models
- Measures
- Reports
- Dashboards

Conceptually:

```text
Fabric Warehouse
       ↓
Semantic Model
       ↓
Power BI Report
       ↓
Business User
```

### Why Warehouse Can Work Well for BI

Warehouse provides a familiar relational analytical structure for:

- SQL users
- BI Developers
- Data Analysts
- Semantic model development

This can make downstream reporting easier when analytical tables are designed properly.

## 7.16 Warehouse and Gold Layer

Gold and Warehouse should **not** be treated as identical concepts.

### Gold

Represents the:

> **Business-ready / curated stage of data**

Gold is an architectural concept.

### Warehouse

Represents:

> **A Fabric data store and SQL analytical experience**

Gold data can potentially be served using a Warehouse.

However:

> **Gold = Architectural Layer**

> **Warehouse = Technology / Data Store Choice**

### Example

```text
Silver Data
    ↓
Business Logic
    ↓
Gold Data
    ↓
Fabric Warehouse
    ↓
Semantic Model
    ↓
Power BI
```

The Gold layer describes **what stage the data is in**, while Warehouse describes **where/how structured analytical data may be served**.

This distinction is important.

## 7.17 Choosing Between Lakehouse and Warehouse

Before choosing between Lakehouse and Warehouse, ask questions based on the actual workload.

### Question 1

Do I need Spark / PySpark and flexible file processing?

→ **Lakehouse is likely suitable**

### Question 2

Is the workload primarily relational and SQL-based?

→ **Warehouse may be suitable**

### Question 3

Do I need raw or semi-structured file processing?

→ **Lakehouse is generally stronger**

### Question 4

Do I need a structured dimensional SQL analytical environment?

→ **Warehouse is generally stronger**

### Question 5

Do I need both engineering flexibility and SQL analytical serving?

→ **Using both may be appropriate**

### Decision Summary

```text
Need Spark / Files / Flexible Engineering?
                  ↓
              Lakehouse

Need Structured Relational SQL Analytics?
                  ↓
              Warehouse

Need Both?
                  ↓
        Lakehouse + Warehouse
```

### Practical Architecture

A complete Fabric solution could look like:

```text
Source Systems
      ↓
Pipeline
Ingestion
      ↓
Lakehouse — Bronze
Raw
      ↓
Notebook
PySpark Transformation
      ↓
Lakehouse — Silver
Clean
      ↓
Business Transformation
      ↓
Gold / Curated Data
      ↓
Warehouse
Fact + Dimension Tables
      ↓
Semantic Model
      ↓
Power BI
```

This connects multiple Fabric concepts into one architecture.

### Correct Data Types Before Analytical Consumption

Data types should also be correct before analytical data is consumed.

For example:

```text
OrderDate
```

should ideally be represented as a Date rather than Text.

Similarly:

```text
Revenue
```

should normally be numeric rather than String when calculations are required.

Correct data types improve:

- Filtering
- Sorting
- Aggregations
- Relationships
- Date intelligence
- Data validation

### Rerun and Validate the Complete Workflow

After changing transformation logic, it is important to rerun and validate the complete downstream flow.

Conceptually:

```text
Change Transformation
       ↓
Run Complete Notebook
       ↓
Validate Output
       ↓
Run Pipeline
       ↓
Validate Downstream Tables
```

Changing one transformation or one Notebook cell does not automatically guarantee that all downstream outputs are correct.

### Real-World Understanding

The important learning is not:

> **I created a Warehouse and ran SQL.**

A stronger understanding is:

> **I understand when a Fabric Warehouse is appropriate for structured SQL-based analytical workloads. I can organize data using schemas, query relational tables using T-SQL, use Views for reusable data presentation, use Stored Procedures for repeatable SQL processing, and integrate the Warehouse with upstream Fabric engineering and downstream Power BI workloads.**

## 7.18 Interview Understanding

### What is Microsoft Fabric Warehouse?

Microsoft Fabric Warehouse is a relational, SQL-based analytical data warehouse within Fabric.

It supports structured analytical workloads using T-SQL and integrates with the wider Fabric and Power BI ecosystem.

### When Would You Use a Warehouse?

I would consider a Warehouse when the workload is:

- Structured
- Relational
- SQL-centric
- Designed for analytics / BI
- Suitable for dimensional modelling

### What is the Difference Between Lakehouse and Warehouse?

> **Lakehouse provides a flexible data-engineering environment supporting files, Delta tables and Spark, while Warehouse provides a structured relational SQL-first analytical environment.**

The choice depends on the workload.

### Can Lakehouse and Warehouse Be Used Together?

Yes.

For example:

```text
Lakehouse
Raw + Transformation
       ↓
Warehouse
Structured Analytical Serving
       ↓
Power BI
```

Lakehouse may handle ingestion and Spark transformations, while Warehouse serves structured business-ready analytical tables.

### What is a Schema?

A Schema is a logical namespace or container used to organize database objects such as:

- Tables
- Views

### What is a View?

A View is a saved SQL query that presents data as a virtual table.

### Does a View Store the Data?

A normal SQL View primarily stores the query definition rather than creating another physical copy of all result data.

### What is a Stored Procedure?

A Stored Procedure is reusable executable SQL logic stored inside the Warehouse.

### What is the Difference Between a View and Stored Procedure?

> **View = Saved query used to present/query data**

> **Stored Procedure = Reusable SQL logic executed to perform a process/action**

### What is a Fact Table?

A Fact Table contains measurable business events such as:

- Sales
- Orders
- Payments
- Bookings

### What is a Dimension Table?

A Dimension Table contains descriptive information used to analyze Fact data.

Examples include:

- Product
- Customer
- Date
- Region

### What is the Difference Between Gold and Warehouse?

> **Gold is an architectural/business-ready data layer, while Warehouse is a Fabric technology/data store used for relational SQL analytics.**

### How Do You Choose Between Lakehouse and Warehouse?

Use **Lakehouse** when flexible file processing, Spark and data engineering are important.

Use **Warehouse** when structured relational SQL analytics are the primary requirement.

Use both when the solution genuinely benefits from both experiences.
