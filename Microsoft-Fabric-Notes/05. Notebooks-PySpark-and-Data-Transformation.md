# Chapter 5: Notebooks, PySpark and Data Transformation

## 5.1 Fabric Notebooks

A **Fabric Notebook is an interactive development environment used to write and execute code for data engineering, data transformation, exploration and analysis**.

In Microsoft Fabric, Notebooks are commonly used with:

- PySpark
- Apache Spark
- Spark SQL
- Python
- Lakehouse data
- Delta tables

A Notebook contains multiple **cells**, and each cell can contain:

- Code
- Documentation
- Explanations
- Transformation logic

### Simple Understanding

> **Pipeline orchestrates the workflow, while a Notebook performs code-based data processing and transformations.**

### Example

```text
Pipeline
   ↓
Load Raw Data
   ↓
Bronze Layer
   ↓
Notebook
   ↓
Clean and Transform Data
   ↓
Silver Delta Table
```

### Why Do We Use Notebooks?

Notebooks are useful when transformations require more flexibility than simple data movement.

Typical uses include:

- Reading large datasets
- Cleaning data
- Filtering records
- Changing data types
- Creating calculated columns
- Joining datasets
- Aggregating data
- Handling null values
- Removing duplicates
- Applying business rules
- Writing transformed data into Delta tables

A Notebook can also be executed automatically from a Fabric Pipeline.

## 5.2 Apache Spark

**Apache Spark is a distributed data-processing engine designed for processing large datasets.**

Instead of requiring all processing to happen on a single machine, Spark can distribute work across multiple compute resources.

### Conceptual Flow

```text
Large Dataset
     ↓
Split Data into Partitions
     ↓
Process Across Resources
     ↓
Combine Results
```

This makes Spark useful for large-scale data engineering workloads.

### Why Spark?

Spark is useful when:

- Data is large
- Distributed processing is required
- Complex transformations need to be performed
- Multiple processing operations need to scale efficiently

---

## 5.3 PySpark

**PySpark is the Python API for Apache Spark.**

It allows us to use Python-style syntax while taking advantage of Spark's distributed processing engine.

### Simple Understanding

> **Python + Apache Spark = PySpark**

With PySpark, I can:

- Read data
- Create DataFrames
- Filter records
- Transform columns
- Join datasets
- Aggregate data
- Handle null values
- Remove duplicates
- Write Delta tables

without manually managing how every piece of data is distributed across the Spark environment.

---

## 5.4 PySpark vs Pandas

PySpark and Pandas can both be used for data transformation, but they are designed for different processing scenarios.

| PySpark | Pandas |
|---|---|
| Distributed processing | Primarily single-machine processing |
| Designed for large-scale datasets | Excellent for small-to-medium datasets that fit comfortably in memory |
| Uses Apache Spark | Uses local machine resources |
| Processes data across partitions | Primarily processes data in local memory |
| Useful for large data engineering workloads | Excellent for local analysis and smaller transformations |
| Has distributed-processing overhead | Often simpler and faster for smaller workloads |

### Important Understanding

I should **not memorize a fixed rule such as "Pandas is always faster below a particular number of rows."**

Performance depends on:

- Number of rows
- Number of columns
- Data types
- Available memory
- Complexity of transformations
- Hardware
- Spark startup overhead
- Distributed-processing overhead

### Practical Rule

> **Use Pandas when the dataset comfortably fits in memory and distributed processing is unnecessary. Use PySpark when scale or distributed processing makes Spark appropriate.**

## 5.5 Spark DataFrames

A **Spark DataFrame is a distributed collection of structured data organized into named columns**.

It looks conceptually similar to a database table.

| OrderID | Product | Revenue |
|---:|---|---:|
| 101 | Laptop | 70000 |
| 102 | Mobile | 30000 |
| 103 | Tablet | 25000 |

However, a Spark DataFrame is designed for **distributed processing**.

A common variable name is:

```python
df
```

where `df` represents the DataFrame.

### Simple Understanding

> **Spark DataFrame = Structured data that Spark can process across distributed resources.**

## 5.7 `display()` vs `show()`

Both `display()` and `show()` can be used to inspect DataFrame results, but they serve slightly different purposes.

### `show()`

Example:

```python
df.show()
```

`show()` is a Spark DataFrame method.

It prints rows in a text-style tabular output.

Useful for:

- Quick debugging
- Inspecting records
- Checking transformation results

### `display()`

Example:

```python
display(df)
```

In Fabric Notebooks, `display()` provides a richer interactive representation of the DataFrame.

It is useful for visually exploring data.

### Comparison

| `show()` | `display()` |
|---|---|
| Spark DataFrame method | Notebook display functionality |
| Text-style output | Rich interactive output |
| Good for quick debugging | Better for visual exploration |
| Standard Spark syntax | Convenient in Fabric Notebooks |

### Easy Way to Remember

> **`show()` = Quick Spark output**

> **`display()` = Rich Notebook visualization**

## 5.8 Data Transformation

**Data transformation means converting raw data into cleaner and more useful data.**

Raw data may contain:

- Incorrect records
- Cancelled transactions
- Returned transactions
- Zero-value transactions
- Null values
- Duplicate records
- Incorrect data types
- Inconsistent formats
- Unnecessary columns
- Poor column names

Therefore, raw data often needs to be cleaned and transformed before analytical use.

### Important Principle

> **Transformation should be driven by business rules, not simply by what looks unnecessary.**

## 5.9 Bronze-to-Silver Transformation

The main practical transformation covered in my learning was:

```text
Bronze Layer
      ↓
Notebook / PySpark
      ↓
Data Cleaning + Transformation
      ↓
Silver Layer
```

My practical transformation included removing:

- Returned transactions
- Cancelled transactions
- Transactions where Revenue = 0

It also included:

- Correcting data types
- Validating data
- Preparing clean analytical data
- Writing the output as a Silver Delta table

### Complete Practical Flow

```text
Raw Data
   ↓
Bronze
   ↓
Read with PySpark
   ↓
Inspect Data
   ↓
Apply Business Rules
   ↓
Correct Data Types
   ↓
Validate Results
   ↓
Write Silver Delta Table
```

## 5.10 Bronze Layer

The **Bronze Layer contains raw or minimally processed data received from the source**.

The purpose of Bronze is generally to preserve source-aligned data before major business transformations are applied.

### Example

```text
Source CSV
    ↓
Bronze
```

Example Bronze data:

| OrderID | Status | Revenue |
|---:|---|---:|
| 101 | Completed | 500 |
| 102 | Cancelled | 800 |
| 103 | Returned | 300 |
| 104 | Completed | 0 |
| 105 | Completed | 900 |

At this stage, the data can still contain records unsuitable for final analytics.

### Why Not Clean Bronze Directly?

If we continuously overwrite the raw data, we may lose the ability to:

- Reprocess data
- Investigate source issues
- Apply new transformation logic later
- Audit what originally arrived
- Recover from incorrect transformations

Therefore:

```text
Bronze
Raw / Source-Aligned Data
        ↓
Silver
Cleaned / Validated Data
```

rather than modifying the only copy of the original data.

> **Bronze should generally preserve the source-aligned data so that it can be reprocessed, audited and troubleshot when needed.**

---

## 5.11 Silver Layer

The **Silver Layer contains cleaned, validated and transformed data**.

Using the practical rules:

- Remove cancelled orders
- Remove returned orders
- Remove zero-revenue transactions

the earlier Bronze example becomes:

| OrderID | Status | Revenue |
|---:|---|---:|
| 101 | Completed | 500 |
| 105 | Completed | 900 |

Therefore:

> **Bronze = Raw / Source-Aligned Data**

> **Silver = Cleaned + Validated + Transformed Data**

### Why Delta for Silver?

Silver data needs to be reliable and manageable.

Delta provides capabilities such as:

- ACID transactions
- Schema management
- Versioning
- Efficient Parquet-based storage
- Update and delete capabilities

Therefore:

```text
Bronze
   ↓
PySpark
   ↓
Silver Delta Table
```

is a natural Fabric data-engineering pattern.

## 5.12 Filtering Data

Filtering is one of the most common PySpark transformations.

Conceptually:

```python
df_filtered = df.filter(...)
```

We may need to filter records such as:

```text
Status = Cancelled
```

or:

```text
Status = Returned
```

or:

```text
Revenue = 0
```

### Important Point

Filtering should not be performed simply because a record appears unnecessary.

There should be a **business reason** for excluding it.

For example:

```text
Business Rule:
Returned transactions should not contribute to completed sales revenue.
```

That provides a valid reason for filtering those records.

## 5.13 Handling Null Values

Raw data may contain missing values.

Example:

| CustomerID | City | Revenue |
|---|---|---:|
| C101 | Mumbai | 500 |
| C102 | NULL | 700 |
| C103 | Pune | NULL |

Before handling null values, we should understand what the missing value means.

Possible actions include:

- Keep the null
- Replace it with a default value
- Fill it using another value
- Remove the record
- Flag the record for data-quality review

### Important Practical Rule

> **Do not blindly remove every null value.**

The correct treatment depends on the business meaning.

For example:

**Missing Revenue**

May be critical because Revenue is required for calculations.

**Missing CustomerMiddleName**

May be acceptable because the field may be optional.

---

## 5.14 Removing Duplicates

Duplicate records can cause incorrect analytical results.

Example:

| OrderID | Revenue |
|---:|---:|
| 101 | 500 |
| 101 | 500 |

If this is an accidental duplicate:

```text
500 + 500 = 1000
```

while the correct revenue may actually be:

```text
500
```

PySpark provides methods for removing duplicate records.

However:

> **A duplicate-looking record should only be removed after understanding the business key and business logic.**

Two identical-looking transactions may sometimes represent legitimate separate events.

Therefore, duplicate handling must be based on:

- Business keys
- Transaction identifiers
- Source-system rules
- Business understanding

## 5.15 Changing Data Types

Correct data types are extremely important.

For example:

```text
OrderDate = "2026-08-16"
```

If stored as text, date-based operations become more difficult.

It should ideally use an appropriate **Date** type.

Similarly:

```text
Revenue = "1500"
```

stored as text should generally be converted to a numeric type before calculations.

### Why Correct Data Types Matter

Data types affect:

- Calculations
- Filtering
- Sorting
- Relationships
- Aggregations
- Performance
- Data quality

Changing the `OrderDate` data type was one of the practical steps performed during the Bronze-to-Silver transformation.

## 5.18 Lazy Evaluation

An important Spark concept is **Lazy Evaluation**.

Spark does not necessarily execute every transformation immediately when the transformation statement is written.

Instead, Spark can build a logical transformation plan.

Conceptually:

```text
Read
 ↓
Filter
 ↓
Select
 ↓
Transform
```

Spark prepares the processing plan.

An action such as:

- Displaying data
- Counting rows
- Writing output

can trigger the actual computation.

### Why Lazy Evaluation?

Lazy evaluation allows Spark to analyze and optimize the execution plan before processing the data.

### Simple Understanding

> **Transformations describe what should happen; an Action triggers computation.**

---

## 5.19 Transformations vs Actions

Spark operations can broadly be understood as **Transformations** and **Actions**.

### Transformations

Transformations define processing logic and normally create another DataFrame or transformation plan.

Examples include:

```python
filter()
select()
withColumn()
drop()
```

### Actions

Actions require Spark to produce a result or execute the processing plan.

Examples include:

```python
show()
count()
```

and writing output.

### Easy Way to Remember

> **Transformation = Define the work**

> **Action = Trigger or produce the result**

### Relationship with Lazy Evaluation

```text
Transformation
     ↓
Transformation
     ↓
Transformation
     ↓
Spark Builds Plan
     ↓
Action
     ↓
Execution
```

## 5.20 Spark Partitions

Spark divides data into **Partitions** so processing can be distributed.

Conceptually:

```text
Large Dataset
      ↓
Partition 1
Partition 2
Partition 3
Partition 4
      ↓
Process Across Available Resources
      ↓
Combined Result
```

This is one of the fundamental reasons Spark can process large datasets efficiently.

### Important

More partitions do **not automatically mean better performance**.

Too few partitions may:

- Limit parallelism
- Reduce distributed-processing efficiency

Too many small partitions may:

- Create unnecessary overhead
- Increase task-management cost

Therefore:

> **Partition strategy depends on workload size, data characteristics and processing requirements.**

### Pipeline + Notebook Relationship

Another important architectural relationship is:

```text
Pipeline
   ↓
Controls Workflow
   ↓
Notebook
   ↓
Performs Transformation
```

Example:

```text
Pipeline
   ↓
Copy Raw Sales Data
   ↓
Bronze
   ↓
Run Notebook
   ↓
PySpark Transformation
   ↓
Silver
```

The Notebook does not replace the Pipeline, and the Pipeline does not replace the Notebook.

They solve different problems and work together.

> **Pipeline = Orchestration**

> **Notebook = Transformation**

## 5.21 Data Validation

A transformation is not complete simply because the Notebook executes without errors.

We should validate the resulting data.

### Example

Before transformation:

```text
10,000 Rows
```

After transformation:

```text
8,500 Rows
```

Question:

> **Why were 1,500 rows removed?**

Suppose the business rules explain:

```text
700 Cancelled
+
500 Returned
+
300 Zero-Revenue
=
1,500 Removed Rows
```

Then the transformation result is explainable.

### Important Data Engineering Mindset

> **Successful execution does not automatically mean correct data.**

### Technical Success vs Business Correctness

These are different concepts.

**Technical Success**

```text
Notebook executed successfully.
```

**Business Correctness**

```text
Output follows the intended business rules.
```

A Notebook could execute perfectly while accidentally removing every completed transaction.

Technically:

```text
SUCCESS
```

Business result:

```text
WRONG
```

Therefore:

> **Always validate the transformed data, not just the execution status.**

### Practical Transformation Validation

After transformation, check:

- Row counts
- Null values
- Duplicate records
- Data types
- Business rules
- Expected columns
- Revenue or other important metrics
- Destination table

## 5.22 Interview Understanding

### What is a Fabric Notebook?

A Fabric Notebook is an interactive development environment used for code-based:

- Data engineering
- Data transformation
- Data exploration
- Analysis

It can work with technologies such as PySpark, Spark SQL and Lakehouse data.

### What is Apache Spark?

Apache Spark is a distributed data-processing engine designed to process large datasets across multiple computing resources.

### What is PySpark?

PySpark is the **Python API for Apache Spark**.

It allows Python-based code to use Spark's distributed processing capabilities.

### Why use PySpark instead of Pandas?

PySpark is appropriate when distributed processing is required for larger or scalable workloads.

Pandas primarily operates on a single machine and is excellent when the dataset comfortably fits into memory.

The decision should depend on:

- Data size
- Memory
- Transformation complexity
- Available compute
- Processing requirements

rather than using a fixed row-count rule.

### What is a Spark DataFrame?

### What is the Bronze Layer?

Bronze generally stores **raw or minimally processed source-aligned data**.

### What is the Silver Layer?

Silver contains **cleaned, validated and transformed data** that is more reliable for downstream processing.

### Why shouldn't we directly modify Bronze data?

Because preserving Bronze allows us to:

- Reprocess data
- Audit source data
- Troubleshoot problems
- Apply new transformation logic
- Recover from transformation errors

Spark uses Lazy Evaluation, meaning transformations are generally not executed immediately.

Spark partitions data so processing can be distributed across available compute resources.

### What is the difference between Pipeline and Notebook?

> **Pipeline = Orchestration**

> **Notebook = Code-based transformation**

A Pipeline can execute a Notebook as part of an automated workflow.

### Why is data validation important?

Because successful technical execution does not guarantee that the resulting data is business-correct.

The transformed dataset must be validated against the intended business rules.
