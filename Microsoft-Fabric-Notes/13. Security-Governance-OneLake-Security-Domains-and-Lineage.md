# Chapter 13: Security, Governance, OneLake Security, Domains and Lineage

---

## 13.1 Why Security and Governance Matter

Until this stage, most of the Microsoft Fabric learning focused on:

- Ingesting data
- Transforming data
- Building Bronze, Silver and Gold layers
- Creating Warehouses
- Modelling data
- Building Power BI reports
- Monitoring Pipelines

However, a production solution must also answer:

> **Who can access the data?**

> **What can each person see?**

> **Who can modify the solution?**

> **Where did the data come from?**

> **Who owns it?**

> **How do we control and manage it across the organization?**

This is where **Security and Governance** become important.

### Security and Governance Across the Complete Architecture

Security should be considered throughout the complete data lifecycle.

```text
Source
  ↓
Pipeline
  ↓
Bronze
  ↓
Silver
  ↓
Gold
  ↓
Warehouse / Lakehouse
  ↓
Semantic Model
  ↓
Power BI
  ↓
Business User
```

At every stage we should ask:

- Who can edit?
- Who can read?
- What data can each user access?
- Is sensitive data protected?
- Who owns the asset?
- Can we trace the lineage?

Security should therefore not be treated as something added only after the Power BI report is complete.

### Practical Developer Mindset

A beginner may say:

> **I created a Pipeline, Lakehouse, Warehouse and Power BI Report.**

A practical developer also asks:

- Who can access it?
- Who can edit it?
- What data can each user see?
- Where did the data come from?
- Where is it going?
- Who owns it?
- Is sensitive data protected?
- Can it be audited?
- Can it be maintained safely?

### Important Understanding

> **A complete data solution is not only about moving and visualizing data. It must also be secure, governed, traceable and maintainable.**

## 13.2 Security vs Governance

Security and Governance are related, but they are not the same thing.

### Security

Security mainly asks:

> **Who can access what?**

It focuses on protecting:

- Data
- Workspaces
- Fabric items
- Reports
- Tables
- Folders
- Rows
- Columns

### Governance

Governance is broader.

It asks:

> **How should data be managed, controlled, documented and monitored across the organization?**

Governance can include:

- Access control
- Ownership
- Documentation
- Lineage
- Naming standards
- Data classification
- Auditability
- Lifecycle management
- Sharing
- Compliance

### Easy Way to Remember

> **Security = Who can access it?**

> **Governance = How do we control and manage it properly?**

### Simple Comparison

| Security | Governance |
|---|---|
| Controls access | Controls overall management |
| Protects data/resources | Establishes standards and processes |
| Who can see/edit? | Who owns/manages/documents? |
| Permissions | Policies + ownership + lineage + lifecycle |

## 13.3 Fabric Security Layers

Security in Microsoft Fabric should not be thought of as one single permission setting.

Fabric uses multiple layers of security.

Examples include:

- Workspace roles
- Item-level permissions
- OneLake Security
- Semantic Model security
- SQL security
- Row-Level Security
- Column-Level Security
- Other applicable object/data security mechanisms

### Conceptual Security Layers

```text
Organization
     ↓
Workspace
     ↓
Fabric Item
     ↓
Underlying Data
     ↓
Semantic / SQL Security
     ↓
Business User
```

Different layers answer different security questions.

### Quick Comparison

| Security Layer | Main Question |
|---|---|
| Workspace Role | What can this user do in the Workspace? |
| Item Permission | Can this user access this specific item? |
| OneLake Security | Which underlying data can this user access? |
| RLS | Which rows can this user see? |
| CLS | Which columns can this user see? |
| Semantic Model Security | What can this user access through the analytical model? |

### Important Principle

> **Security should be designed according to the actual access requirement and access path.**

Not every requirement should be solved using the same security mechanism.

## 13.4 Workspace Roles

Fabric Workspaces provide roles such as:

- Admin
- Member
- Contributor
- Viewer

These roles determine what users can do within the Workspace.

### General Understanding

| Role | General Purpose |
|---|---|
| **Admin** | Highest level of Workspace control |
| **Member** | Strong collaboration and management capabilities |
| **Contributor** | Create and modify content |
| **Viewer** | Primarily consume/view content |

### Example

Suppose a Workspace contains:

```text
Sales Pipeline
Sales Lakehouse
Sales Warehouse
Sales Semantic Model
Sales Report
```

A developer may require permissions to modify these assets.

A business manager who only consumes the report may not require the same access.

### Important Principle

> **Not everyone should receive Admin or Member access simply because it is easier.**

This directly connects to the **Principle of Least Privilege**.

---

## 13.5 Principle of Least Privilege

The **Principle of Least Privilege** means:

> **Give users only the access they actually need to perform their work.**

### Example

If a business manager only needs to view a Power BI Report, they should not automatically receive permission to:

- Edit Pipelines
- Modify Notebooks
- Delete tables
- Change Workspace settings
- Modify the Semantic Model

### Practical Rule

> **Minimum necessary access is safer than maximum convenient access.**

### Why Least Privilege Matters

It reduces the risk of:

- Accidental changes
- Unauthorized data access
- Accidental deletion
- Security exposure
- Uncontrolled production modifications

### Simple Example

```text
Business User
     ↓
Needs Report Access
     ↓
Give Report Consumption Access
```

Not:

```text
Business User
     ↓
Needs Report Access
     ↓
Give Full Workspace Admin Access
```

---

## 13.6 Item-Level Permissions

Workspace roles can provide broad access.

Sometimes a user should receive access to only one specific Fabric item.

Example:

A user needs:

```text
Sales Report
```

but should not necessarily access:

```text
Sales Pipeline
Notebook
Lakehouse
Warehouse
Other Reports
```

This is where **Item-Level Permissions** become useful.

### Simple Understanding

> **Workspace Role = Broader access across the Workspace**

> **Item Permission = Access to a specific Fabric item**

### Why Item-Level Permissions Matter

They provide more granular access when users do not require access to the entire Workspace.

Example:

```text
Workspace
   |
   ├── Pipeline
   ├── Lakehouse
   ├── Notebook
   └── Sales Report
           ↑
       User Access
```

The user can be given access according to the actual requirement.

## 13.7 OneLake Security

**OneLake Security provides granular access control over data stored in OneLake.**

A useful distinction is:

> **Workspace Security controls access to Fabric resources.**

> **OneLake Security controls access to underlying data more granularly.**

### Why OneLake Security Matters

Suppose a Lakehouse contains:

```text
Finance
HR
Sales
Marketing
```

A user who requires access to Sales data should not automatically be able to access every Finance or HR dataset.

OneLake Security can help define more precise access.

### Example

```text
Finance Team
     ↓
Finance Data

HR Team
     ↓
HR Data

Sales Team
     ↓
Sales Data
```

### Security Closer to the Data

OneLake Security can support security at levels such as:

- Tables
- Folders
- Rows
- Columns

depending on the supported scenario.

### Simple Understanding

> **OneLake Security protects the data itself, not only the Fabric item that contains it.**

---

## 13.8 OneLake Security Roles

OneLake Security uses **roles** to define access.

Conceptually:

```text
Role
  ↓
Which Data is Accessible
  ↓
Members
  ↓
Who Receives the Access
```

### Example

```text
Role: FinanceReaders

Grant Access:
Finance/Transactions
Finance/Budget

Members:
Finance Users
```

### Easy Way to Remember

> **Role = Which data is allowed**

> **Members = Who receives that access**

### Grant-Based Security

An important concept is that access must be explicitly designed through the appropriate security mechanisms.

Example:

```text
Role:
SalesWestReaders

Grant:
Sales/West

Members:
West Sales Team
```

The members receive access to the permitted scope.

### Important Permission Rule

A simple statement such as:

> **Deny always overrides Grant**

should **not** be memorized as a universal OneLake rule.

Effective permission behavior can depend on:

- Role configuration
- Overlapping permissions
- Access path
- Security mechanism
- How the data is accessed

### Better Rule to Remember

> **Do not assume a universal deny-overrides-grant rule. Design roles carefully and test effective permissions.**

### Security Testing

Security should always be verified using realistic user scenarios.

Example:

```text
Finance User
   ↓
Should See Finance
   ↓
Should Not See HR
```

Do not assume the configuration works only because the role was created successfully.

## 13.9 Table-Level Security

OneLake Security can control access to specific tables in supported scenarios.

Example Lakehouse:

```text
fact_sales
dim_customer
employee_salary
```

Sales analysts may require:

```text
fact_sales
dim_customer
```

but should not necessarily access:

```text
employee_salary
```

### Conceptual Role

```text
Role: SalesAnalysts
        ↓
Grant:
fact_sales
dim_customer
        ↓
No Business Requirement:
employee_salary
```

### Why Table-Level Security Matters

Different tables can have very different sensitivity levels.

For example:

```text
Product Data
```

may be broadly accessible while:

```text
Employee Salary
```

may require highly restricted access.

### Important Principle

> **Access should be based on business requirement, not simply on where the table is stored.**

## 13.10 Folder-Level Security

OneLake can also contain file-based folder structures.

Example:

```text
Files/
   Finance/
   HR/
   Sales/
```

Different teams may require access to different folders.

Example:

```text
Finance Role
      ↓
Files/Finance
```

without automatically requiring access to:

```text
Files/HR
```

### Why Folder-Level Security Matters

It can be useful for:

- File-based ingestion areas
- Department-specific data
- Raw source files
- Segregated business datasets

### Simple Understanding

> **Folder-Level Security controls which file/folder areas users can access.**

## 13.11 Row-Level Security

**Row-Level Security controls which rows of a dataset a user is allowed to access.**

Example:

```text
North Manager → North Rows

South Manager → South Rows
```

### Example Data

| Region | Revenue |
|---|---:|
| North | 100000 |
| South | 90000 |
| East | 80000 |

A North Manager may be allowed to see:

| Region | Revenue |
|---|---:|
| North | 100000 |

### Conceptual Flow

```text
User
  ↓
Security Role
  ↓
Region Rule
  ↓
Allowed Rows
```

### OneLake RLS

In supported scenarios, OneLake Security can apply row-level rules to the underlying data.

Example rule conceptually:

```text
Region = "North"
```

### Simple Understanding

> **RLS = Which rows can I see?**

---

## 13.12 Column-Level Security

Sometimes users can access a table but should not see every column.

Example:

| EmployeeID | Department | Salary |
|---|---|---:|
| 101 | Finance | 80000 |
| 102 | HR | 70000 |

Some users may need:

```text
EmployeeID
Department
```

but should not access:

```text
Salary
```

This is where **Column-Level Security** becomes important.

### Simple Understanding

> **RLS = Which rows can I see?**

> **CLS = Which columns can I see?**

### Why CLS Matters

It can help protect fields such as:

- Salary
- Personal information
- Sensitive financial information
- Confidential business attributes

### Important

Row-level and column-level security solve different problems.

## 13.13 RLS vs OneLake Security

Power BI Semantic Model RLS and OneLake Security are related security concepts, but they should not be treated as identical.

### Semantic Model RLS

Controls rows available through the:

```text
Semantic Model
      ↓
Power BI Report
```

### OneLake Security

Controls access closer to the underlying data in OneLake across supported Fabric access paths.

### Simple Difference

> **Semantic Model RLS = Reporting / Model-Level Security**

> **OneLake Security = Data-Layer Security**

### Example

```text
OneLake
   ↓
Underlying Sales Data
   ↓
Semantic Model
   ↓
Power BI Report
```

Security can potentially exist at more than one level depending on the architecture.

### Important Principle

> **Choose security according to where the data needs to be protected and how users access it.**

## 13.14 Security Through Shortcuts

OneLake Shortcuts do **not** bypass security.

A Shortcut provides a reference to existing data, but the security model still needs to be considered.

### Conceptual Flow

```text
User
  ↓
Shortcut
  ↓
Referenced Data
  ↓
Security Check
```

Creating a Shortcut does not mean:

> **Everyone now automatically has access to the source data.**

### Important Shortcut Security Warning

Security must be designed for the **actual access path**.

For example, security applied through a SQL access path should not automatically be assumed to provide identical protection when the same data is accessed differently through a Shortcut.

### Practical Rule

> **Security through one access path does not automatically guarantee equivalent security through every other access path.**

### Therefore

Whenever Shortcuts are used:

- Understand the source permissions
- Understand how the Shortcut authenticates
- Understand the consuming access path
- Test effective access
- Verify sensitive data remains protected

### Key Lesson

> **Shortcut = Data Reference**

> **Shortcut ≠ Security Bypass**

---

## 13.15 Pass-Through Identity

OneLake Shortcuts can use **Pass-Through Identity** in supported scenarios.

With pass-through behavior, access to the Shortcut target can be evaluated using the signed-in user's identity.

Conceptually:

```text
User
  ↓
Shortcut
  ↓
User Identity Passed Through
  ↓
Source Permission Checked
  ↓
Allowed / Denied
```

### Example

Suppose:

```text
User A
```

has permission to the source data.

Then access through the relevant Shortcut scenario can be evaluated using User A's permissions.

If:

```text
User B
```

does not have the required permission, creating or accessing a Shortcut should not automatically provide unrestricted access.

### Important Understanding

> **Creating a Shortcut does not automatically grant permission to the underlying source data.**

### Why Pass-Through Identity Matters

It allows security to remain connected to the actual identity accessing the underlying data rather than assuming that the Shortcut itself provides unrestricted access.

## 13.16 OneLake Catalog

**OneLake Catalog is a centralized Fabric experience for discovering, exploring and governing Fabric data and items.**

### Simple Understanding

> **OneLake Catalog = Central view of the organization's Fabric data estate**

It can help users understand:

- What data exists?
- Where is it?
- Who owns it?
- Can I trust it?
- How is it governed?
- What can I access?

### Why a Data Catalog Matters

Imagine an organization has:

```text
500 Workspaces
3,000 Lakehouses
1,000 Semantic Models
Thousands of Tables and Reports
```

A user searching for:

```text
Customer Sales Data
```

cannot realistically open every Workspace manually.

A Catalog helps with:

- Discovery
- Search
- Data understanding
- Governance
- Ownership
- Trust

### Important Principle

> **Data is useful only when people can find and understand the correct data.**

### Explore

The Catalog's exploration experience helps users find available Fabric content and determine which assets may be relevant.

This can reduce duplicated effort.

Instead of:

```text
Cannot Find Existing Dataset
        ↓
Create Another Copy
```

the better approach may be:

```text
Search Catalog
      ↓
Find Trusted Existing Data
      ↓
Reuse It
```

### Govern

Governance-oriented experiences help owners and administrators understand areas such as:

- Ownership
- Governance status
- Data estate organization
- Governance gaps
- Areas requiring attention

### Security Visibility

Centralized security visibility can also help answer:

> **Who currently has access?**

This reduces the need to inspect every Workspace or item separately when broader governance visibility is required.

## 13.17 Fabric Domains

A **Fabric Domain is a logical grouping of organizational data around a business area.**

Examples include:

- Sales
- Finance
- HR
- Marketing
- Operations

### Simple Understanding

> **Domain = Business-Oriented Grouping of Data**

### Example Organization

```text
Organization
   |
   ├── Finance Domain
   |
   ├── Sales Domain
   |
   ├── HR Domain
   |
   └── Marketing Domain
```

### Organization by Domains

Each Domain can logically group relevant Workspaces.

Example:

```text
Organization
   |
   ├── Finance Domain
   |      ├── Finance Reporting Workspace
   |      └── Finance Engineering Workspace
   |
   ├── Sales Domain
   |      ├── Sales BI Workspace
   |      └── Sales Data Engineering Workspace
   |
   └── HR Domain
          └── HR Analytics Workspace
```

### Why Domains Matter

Domains help improve:

- Data ownership
- Discoverability
- Business organization
- Governance
- Delegated management
- Clear responsibility

### Practical Principle

> **Organize the data estate according to meaningful business areas rather than treating every Workspace as an isolated object.**

## 13.18 Domain vs Workspace

Domain and Workspace should not be confused.

### Workspace

A Workspace contains actual Fabric items.

Example:

```text
Sales Analytics Workspace
```

may contain:

```text
Lakehouse
Pipeline
Notebook
Semantic Model
Report
```

### Domain

A Domain groups related Workspaces or organizational data under a broader business area.

Example:

```text
Sales Domain
   |
   ├── Sales Analytics Workspace
   ├── Sales Operations Workspace
   └── Sales Forecasting Workspace
```

### Simple Difference

> **Workspace = Project / Team Container**

> **Domain = Higher-Level Business Grouping**

### Enterprise Structure

A useful mental model is:

```text
Organization
     ↓
Domain
     ↓
Workspaces
     ↓
Fabric Items
```

This is more scalable than treating hundreds of Workspaces as unrelated objects.

## 13.19 Data Lineage

**Data Lineage shows where data came from, how it moved or transformed and where it is being consumed.**

### Simple Question

> **Where is the data coming from and where is it going?**

### Example

```text
SQL Database
     ↓
Pipeline
     ↓
Bronze Lakehouse
     ↓
Notebook
     ↓
Silver
     ↓
Warehouse
     ↓
Semantic Model
     ↓
Power BI Report
```

This complete chain represents **Data Lineage**.

### Why Lineage Matters

Suppose management reports:

> **The Revenue number in Power BI is wrong.**

Without lineage, troubleshooting may be difficult.

With lineage:

```text
Power BI Report
      ↓
Semantic Model
      ↓
Warehouse
      ↓
Notebook Transformation
      ↓
Silver
      ↓
Bronze
      ↓
Source
```

we can trace the data backward through the solution.

### Uses of Lineage

- Troubleshooting
- Impact analysis
- Governance
- Auditing
- Dependency understanding
- Change management

### Lineage vs Monitoring

These concepts solve different problems.

**Monitoring**

asks:

> **Did this process run successfully?**

**Lineage**

asks:

> **How are these data assets connected?**

Example:

```text
Monitoring:
Pipeline failed at 6:00 AM
```

vs:

```text
Lineage:
Pipeline → Lakehouse → Warehouse → Semantic Model → Report
```

### Easy Way to Remember

> **Monitoring = Operational Status**

> **Lineage = Data Dependency Flow**

## 13.20 Impact Analysis

Lineage supports **Impact Analysis**.

Impact Analysis helps us understand what downstream assets may be affected if an upstream object changes.

### Example

Suppose someone wants to:

```text
Delete fact_sales
```

Before deleting it, ask:

> **What depends on this table?**

Possible dependency:

```text
fact_sales
    ↓
Semantic Model
    ↓
Executive Dashboard
```

Deleting or changing `fact_sales` may therefore break the downstream report.

### Another Example

```text
Change Column Name
Revenue → SalesAmount
```

Potential impact:

```text
Warehouse Table
      ↓
Semantic Model Measure
      ↓
Power BI Visual
```

### Important Principle

> **Before changing an important upstream asset, understand its downstream dependencies.**

### Why Impact Analysis Matters

It supports safer:

- Schema changes
- Table deletion
- Column renaming
- Pipeline changes
- Model changes
- Production deployments

## 13.21 Ownership

Governance should establish clear ownership for important data assets.

Example:

| Asset | Owner |
|---|---|
| Sales Lakehouse | Data Engineering Team |
| Finance Warehouse | Finance Data Team |
| Executive Dashboard | BI Team |

Ownership helps answer:

- Who approves changes?
- Who understands the data?
- Who handles quality problems?
- Who should users contact?
- Who is responsible for access decisions?

### Without Ownership

```text
Problem Found
     ↓
Nobody Knows Who Owns the Data
     ↓
Delayed Resolution
```

### With Ownership

```text
Problem Found
     ↓
Known Data Owner
     ↓
Investigation
     ↓
Resolution
```

### Important Principle

> **A governed data asset should have clear responsibility.**

Without ownership, important data can become effectively unmanaged.

## 13.22 Naming Standards

Governance also includes consistent naming standards.

Avoid unclear names such as:

```text
Table1
FinalTable
NewTable2
Test123
```

Prefer meaningful names such as:

```text
fact_sales
dim_customer
dim_product
pl_daily_sales_ingestion
nb_bronze_to_silver_sales
```

### Why Naming Standards Matter

Consistent naming improves:

- Discovery
- Understanding
- Maintenance
- Collaboration
- Governance
- Troubleshooting

### Example Prefixes

```text
pl_   → Pipeline
nb_   → Notebook
df_   → Dataflow
lh_   → Lakehouse
wh_   → Warehouse
fact_ → Fact Table
dim_  → Dimension Table
```

These are examples rather than mandatory Fabric naming standards.

### Important Rule

> **The exact naming convention can vary, but it should be consistent and understandable.**

## 13.26 Development, Test and Production

A governed production environment should normally separate different stages of solution development.

Conceptually:

```text
Development
     ↓
Test
     ↓
Production
```

### Development

Used to:

- Build
- Experiment
- Develop transformations
- Make changes

### Test

Used to:

- Validate functionality
- Validate data
- Test security
- Test dependencies
- Confirm changes

### Production

Contains the:

> **Business-approved operational solution**

### Why Direct Production Changes Are Risky

Suppose a developer directly changes a production Notebook and introduces incorrect logic.

That change might affect:

```text
Notebook
   ↓
Silver
   ↓
Gold
   ↓
Warehouse
   ↓
Semantic Model
   ↓
Power BI Report
```

One incorrect change can therefore affect the entire downstream chain.

### Better Approach

```text
Develop
   ↓
Test
   ↓
Validate
   ↓
Deploy
```

### Important Principle

> **Production should be controlled rather than treated as an experimentation environment.**

### Lifecycle Governance

Development → Test → Production supports:

- Safer changes
- Better testing
- More predictable releases
- Reduced production risk
- Better governance

---

### What is Column-Level Security?

> **CLS controls which columns a user can see.**

Example:

A user may access:

```text
EmployeeID
Department
```

but not:

```text
Salary
```

---

### Semantic Model RLS vs OneLake Security?

> **Semantic Model RLS = Reporting / Model-Level Security**

> **OneLake Security = Underlying Data-Layer Security**

---

### Does a Shortcut Bypass Security?

No.

> **Shortcut ≠ Security Bypass**

Security still needs to be designed according to the Shortcut source, identity and actual access path.

---

### What is Pass-Through Identity?

Pass-through identity allows the signed-in user's identity to participate in authorization against the underlying Shortcut source in supported scenarios.

Conceptually:

```text
User
  ↓
Shortcut
  ↓
User Identity
  ↓
Source Permission
```

### What is OneLake Catalog?

OneLake Catalog is a centralized Fabric experience for:

- Discovering
- Exploring
- Understanding
- Governing

Fabric data and items.

---

### Why is a Data Catalog Important?

Because users need to be able to:

- Find trusted data
- Understand what it represents
- Identify ownership
- Avoid creating unnecessary duplicate datasets

---

### What is a Fabric Domain?

A Fabric Domain logically organizes data and Workspaces around a business area such as:

```text
Sales
Finance
HR
Marketing
```

---

### Domain vs Workspace?

> **Workspace = Project / Team Container**

> **Domain = Higher-Level Business Grouping**

---

### What is Data Lineage?

Data Lineage shows:

> **Where data came from, how it moved or transformed and where it is consumed.**

Example:

```text
Source
   ↓
Pipeline
   ↓
Lakehouse
   ↓
Warehouse
   ↓
Semantic Model
   ↓
Report
```

---

### What is Impact Analysis?

Impact Analysis identifies which downstream assets may be affected by changing an upstream asset.

Example:

```text
fact_sales
   ↓
Semantic Model
   ↓
Executive Dashboard
```

Changing `fact_sales` may therefore affect the dashboard.

---

### Monitoring vs Lineage?

> **Monitoring = Did the process run correctly?**

> **Lineage = How are the data assets connected?**

---

### Why is Ownership Important?

Because important data should have someone responsible for:

- Access
- Quality
- Changes
- Business understanding
- Troubleshooting

---

### Why are Naming Standards Important?

They improve:

- Discovery
- Maintainability
- Collaboration
- Governance
- Troubleshooting

---

### Why is Documentation Important?

Because important data assets should remain understandable even when the original developer is unavailable.

---

### What is Data Classification?

Data Classification groups data according to its sensitivity.

Examples:

```text
Internal
Confidential
Highly Sensitive
```

This helps determine appropriate security and governance controls.

---

### What is Auditability?

Auditability is the ability to understand important access and change activity.

Examples:

- Who changed permissions?
- Who changed an asset?
- Who accessed sensitive data?

---

### Why Separate Development, Test and Production?

Because uncontrolled direct production changes can affect multiple downstream systems.

A safer lifecycle is:

> **Develop → Test → Validate → Deploy**

### Practical Example — HR Analytics

Suppose we build:

```text

    ↓
HR Analytics Workspace
```

containing:

- HR Pipeline
- HR Lakehouse
- HR Warehouse
- HR Semantic Model
- HR Report

Security requirements may include:


```text
Permitted Business Scope
```

**Other Employees**

```text

No Access to Sensitive HR Data
```

- Tables follow naming standards
- Lineage is visible
- Sensitive data is classified

This is the difference between:

> **Building a governed HR analytics solution**

The important learning is not:

> **I know how to assign permissions.**

> **I understand that security and governance must be designed across the complete Fabric architecture. Workspace roles, item permissions, OneLake Security and Semantic Model security solve different access problems, while Domains, Catalog, Lineage, Ownership, Documentation, Classification and lifecycle management help keep the overall data estate governed and maintainable.**

## 13.28 Key Takeaways

1. **Security and Governance are related but different.**

> **Security = Who can access it?**

> **Governance = How do we control and manage it properly?**

2. Fabric security is **multi-layered**.

3. Important security layers can include:

   - Workspace Roles
   - Item Permissions
   - OneLake Security
   - Semantic Model Security
   - Row-Level Security
   - Column-Level Security

4. Always follow the **Principle of Least Privilege**:

> **Give users only the permissions required for their work.**

5. Workspace Roles provide broader Workspace-level access.

6. Item-Level Permissions provide more specific item access.

7. OneLake Security provides more granular control over underlying data.

8. OneLake Security Roles can define:

> **Which Data is Accessible + Who Receives the Access**

9. Do not memorize:

> **Deny always overrides Grant**

as a universal OneLake rule.

A safer principle is:

> **Design overlapping access carefully and test effective permissions.**

10. Table-Level Security can restrict access to particular tables.

11. Folder-Level Security can restrict access to specific file/folder areas.

12. The key distinction is:

> **RLS = Which Rows Can I See?**

> **CLS = Which Columns Can I See?**

13. Semantic Model RLS and OneLake Security operate at different security layers.

14. A Shortcut does **not** bypass security.

15. Security must be designed according to the **actual access path**.

16. Pass-Through Identity can allow the signed-in user's identity to participate in source authorization in supported Shortcut scenarios.

17. **OneLake Catalog** helps users discover, explore and govern Fabric assets.

18. A useful principle is:

> **Data is useful only if people can find and understand the correct data.**

19. Fabric Domains organize data around business areas such as:

```text
Sales
Finance
HR
Marketing
Operations
```

20. A useful enterprise structure is:

```text
Organization
     ↓
Domain
     ↓
Workspaces
     ↓
Fabric Items
```

21. The difference is:

> **Workspace = Project / Team Container**

> **Domain = Higher-Level Business Grouping**

22. **Data Lineage** answers:

> **Where did the data come from, how did it change and where is it being used?**

23. Example lineage:

```text
Source
   ↓
Pipeline
   ↓
Bronze
   ↓
Notebook
   ↓
Silver
   ↓
Warehouse
   ↓
Semantic Model
   ↓
Power BI Report
```

24. Lineage helps with:

   - Troubleshooting
   - Governance
   - Auditing
   - Dependency understanding
   - Change management

25. **Impact Analysis** helps identify what downstream assets may be affected by an upstream change.

26. The difference is:

> **Monitoring = Did it run?**

> **Lineage = How is everything connected?**

27. Governance should establish clear **Ownership**.

28. Governance should also establish consistent **Naming Standards**.

29. Important data assets should have proper **Documentation**.

30. Sensitive data should be classified and protected according to its business sensitivity.

31. Auditability helps answer:

   - Who accessed it?
   - Who changed it?
   - Who changed permissions?
   - Who published it?

32. Production solutions should normally follow a controlled lifecycle:

> **Development → Test → Production**

33. Direct uncontrolled production changes can affect:

```text
Silver
   ↓
Gold
   ↓
Warehouse
   ↓
Semantic Model
   ↓
Reports
```

34. A governed architecture should consider security throughout the full flow:

```text
Source
   ↓
Pipeline
   ↓
Bronze
   ↓
Silver
   ↓
Gold
   ↓
Warehouse / Lakehouse
   ↓
Semantic Model
   ↓
Power BI
   ↓
Business User
```

35. The practical-developer mindset is:

> **Do not only ask whether you can build the solution. Also ask whether you can secure it, govern it, trace it and maintain it safely in production.**

36. The complete governance mindset can be summarized as:

> **Access + Ownership + Lineage + Naming + Documentation + Classification + Auditability + Lifecycle + Domains + Catalog**

37. The most important principle is:

> **A complete Fabric solution must ensure that the right people have the right access, sensitive data is protected, assets can be discovered and traced, ownership is clear, and the solution remains secure and manageable in production.**
