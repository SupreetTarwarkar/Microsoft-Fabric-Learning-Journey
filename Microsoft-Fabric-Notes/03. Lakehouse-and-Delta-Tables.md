# Chapter 3: Lakehouse and Delta Tables

---

## 3.1 What is a Lakehouse?

A **Lakehouse combines the flexibility of a Data Lake with important analytical capabilities traditionally associated with a Data Warehouse**.

In Microsoft Fabric, a Lakehouse allows us to store different types of data in OneLake and work with that data using technologies such as:

- Apache Spark
- PySpark
- SQL
- Notebooks
- Power BI

A simple way to remember:

> **Lakehouse = Data Lake flexibility + Warehouse-style analytical capabilities**

A Lakehouse is especially useful when we need to:

- Store raw data
- Work with different file formats
- Transform large datasets
- Use Spark and PySpark
- Create reliable analytical tables
- Query data using SQL
- Use the data in Power BI

### Lakehouse vs Traditional Data Lake

A **Data Lake** primarily provides flexible storage for:

- Structured data
- Semi-structured data
- Unstructured data
- Raw files

A **Lakehouse** adds stronger table and analytical capabilities to the flexibility of a Data Lake.

Therefore:

> **Lakehouse tries to combine Data Lake flexibility with Data Warehouse-style reliability and analytics.**

The detailed comparison between **Lakehouse and Fabric Warehouse** is covered separately after understanding Fabric Warehouse.

### Real-World Understanding

The important lesson is not simply:

> **I know how to create a Lakehouse.**

A more practical understanding is:

> **I understand why a Lakehouse is useful when an organization needs flexible file-based storage, Spark transformations, reliable Delta tables, SQL analytics and Power BI consumption within the same Fabric environment.**

## 3.2 Why Do We Need a Lakehouse?

Organizations receive data in many different formats.

Examples include:

- CSV
- Parquet
- JSON
- Excel
- Database extracts
- Application data
- Semi-structured data

A traditional Data Warehouse mainly focuses on structured analytical data.

A Lakehouse provides more flexibility because we can first land data in its original or raw form and then progressively transform it.

### Example

```text
CSV Sales Files
       ↓
Lakehouse - Raw Data
       ↓
PySpark Transformation
       ↓
Clean Delta Tables
       ↓
Business-Ready Tables
       ↓
Power BI
```

This makes the Lakehouse useful for both **data engineering and analytics workflows**.

### Practical Flow

Suppose I receive:

```text
sales.csv
```

The file can first be stored in:

```text
Lakehouse
    ↓
Files
```

Then:

```text
Lakehouse Files
       ↓
Notebook / PySpark
       ↓
Clean and Transform
       ↓
Delta Table
       ↓
SQL / Semantic Model
       ↓
Power BI
```

This is the practical relationship to remember rather than treating Lakehouse, Delta, SQL and Power BI as unrelated technologies.

## 3.4 Files and Tables in a Lakehouse

One of the most important things to understand about a Fabric Lakehouse is that it exposes two main areas:

### Files

Used for storing general files such as:

- CSV
- JSON
- Parquet
- Images
- Other file formats

### Tables

Used for structured tables that can be queried and analyzed.

| Area | Purpose |
|---|---|
| **Files** | Store raw or general files |
| **Tables** | Store structured analytical tables |

### Simple Understanding

> **Files = File-based storage**

> **Tables = Structured tables for analytics**

### Example of Lakehouse Structure

Suppose I create:

```text
Lakehouse: lh_sales
```

It may contain:

**Files**

```text
Files/raw/sales.csv
Files/raw/customers.csv
Files/raw/products.csv
```

**Tables**

```text
Tables/sales
Tables/customers
Tables/products
```

The **Files** area may hold the original source files, while the **Tables** area can contain structured tables created from that data.

### Important Difference — File vs Table

| File | Delta Table |
|---|---|
| Raw/general file storage | Structured table |
| Can be CSV, JSON, Parquet, etc. | Data commonly stored using Delta |
| Mainly file-oriented | Table-oriented |
| Useful for raw ingestion | Useful for reliable analytics and transformation |
| Limited table management | Transaction and schema-management capabilities |

Therefore:

> **Not every file inside a Lakehouse automatically becomes a Lakehouse table.**

This is an important distinction.

## 3.5 What is Delta Lake?

One of the most important concepts behind Fabric Lakehouse tables is **Delta Lake**.

Delta Lake is an open-source storage framework that extends Parquet-based data with capabilities required for more reliable data processing.

A simple way to understand it:

> **Delta = Parquet data files + transaction log + additional table-management capabilities**

A Delta table is **not simply a completely different physical file format replacing Parquet**.

Delta tables use:

- **Parquet files** for the actual data
- **Delta transaction log** for tracking table changes and transactions

Therefore:

> **Parquet provides the physical data storage, while Delta adds reliability and table-management capabilities around it.**

---

## 3.6 Delta Table Structure

Conceptually, a Delta table contains:

```text
Delta Table
    │
    ├── Parquet Data Files
    │
    └── _delta_log
```

The **Parquet files** contain the actual table data.

The **`_delta_log`** contains information about:

- Transactions
- Table changes
- Versions
- Schema information
- Files belonging to the table

### Easy Formula

> **Delta Table = Parquet Files + Delta Transaction Log**

This is one of the most important concepts to remember.

---

## 3.7 CSV vs Parquet vs Delta

CSV, Parquet and Delta serve different purposes.

### CSV

CSV is useful for exchanging and storing simple tabular data, but it has limitations when used as primary analytical table storage.

Examples:

- No transaction log
- Weak schema handling
- No ACID transaction support
- No built-in table version history
- Less efficient for large analytical queries compared with columnar formats

### Parquet

Parquet is an efficient **columnar file format** designed for analytical workloads.

Benefits include:

- Columnar storage
- Efficient compression
- Better analytical query performance
- Schema information

However, raw Parquet files do not provide all the table-management capabilities needed for reliable data engineering.

### Delta

Delta adds a transaction layer and table-management capabilities on top of Parquet.

### Comparison

| Feature | CSV | Parquet | Delta |
|---|---|---|---|
| Columnar storage | No | Yes | Yes |
| Compression efficiency | Lower | High | High |
| Schema information | Limited | Yes | Yes |
| Transaction log | No | No | **Yes** |
| ACID transactions | No | No | **Yes** |
| Table versioning | No | No | **Yes** |
| Reliable updates/deletes | Difficult | Difficult | **Supported** |
| Good for analytics | Limited | Good | **Very Good** |

### Important Understanding

> **Parquet provides efficient storage. Delta adds reliability and table-management capabilities on top of Parquet.**

### Best Short Answer

> **Delta uses Parquet for storing data but adds a transaction log and table-management capabilities that raw Parquet files do not provide.**

### Simple Comparison to Remember

> **CSV = Basic file**

> **Parquet = Efficient columnar file**

> **Delta = Parquet + transaction log + reliable table capabilities**

## 3.8 ACID Transactions

One of the major benefits of Delta is support for **ACID transactions**.

ACID stands for:

### Atomicity

A transaction should either complete successfully or not be applied.

Example:

If a data operation fails halfway, we do not want a partially completed table update.

### Consistency

Data should remain in a valid and consistent state before and after a transaction.

### Isolation

Multiple operations should not interfere with each other in a way that produces incorrect results.

### Durability

Once a transaction is successfully committed, the change should persist.

### Simple Understanding

> **ACID makes data operations more reliable and consistent.**

This becomes particularly important when multiple data processes work with the same analytical tables.

### ACID Summary

```text
A → Atomicity
C → Consistency
I → Isolation
D → Durability
```

---

## 3.9 Delta Transaction Log

The **Delta transaction log** is one of the key reasons Delta tables provide capabilities beyond ordinary Parquet files.

The transaction log records information about changes made to the table.

For example:

```text
Version 0
Initial data loaded
       ↓
Version 1
New records inserted
       ↓
Version 2
Some records updated
       ↓
Version 3
Additional data loaded
```

Because Delta maintains transaction history, it can support capabilities such as:

- ACID transactions
- Table versioning
- Time travel
- Reliable updates
- Schema management

### Important

The transaction log helps Delta understand the current state of the table and which data files belong to each committed version.

---

## 3.10 Delta Table Versioning

Every committed change to a Delta table creates a new table version.

Conceptually:

```text
Version 0 → Initial Table

Version 1 → New Data

Version 2 → Updated Data

Version 3 → More Data
```

The transaction log records these changes.

This does **not mean that a completely separate copy of the entire table must be created for every version**.

Instead, Delta tracks which underlying files belong to each table version.

### Why Versioning Matters

Versioning supports capabilities such as:

- Historical inspection
- Debugging
- Time travel
- Audit-related analysis
- Comparing changes between table states

---

## 3.11 Time Travel

Because Delta maintains table versions, previous versions of a table can be queried when they are still available.

This capability is commonly called **Time Travel**.

### Example

Suppose:

```text
Monday
Correct Data
     ↓
Tuesday
Incorrect Transformation
     ↓
Wednesday
Problem Discovered
```

With Delta history, it may be possible to inspect an earlier version of the table.

### Why is Time Travel Useful?

- Debugging
- Auditing
- Comparing historical versions
- Recovering from certain data mistakes

### Important

> **Time Travel should not be treated as a permanent backup strategy.**

Historical versions depend on the underlying files and applicable retention or cleanup policies.

## 3.12 Schema Enforcement

Delta can enforce the expected structure of a table.

Suppose a table expects:

| Column | Type |
|---|---|
| OrderID | Integer |
| OrderDate | Date |
| Revenue | Decimal |

If incoming data does not match the expected schema, Delta can help prevent incompatible data from being written incorrectly.

This is called **Schema Enforcement**.

### Why is Schema Enforcement Important?

Without proper schema control, bad data could enter analytical tables and later cause:

- Reporting errors
- Transformation failures
- Incorrect calculations
- Data quality problems

### Simple Understanding

> **Schema Enforcement protects the table from incompatible data.**

---

## 3.13 Schema Evolution

Sometimes the structure of source data legitimately changes.

For example, originally the table contains:

```text
OrderID
CustomerID
Revenue
```

Later a new column arrives:

```text
Discount
```

Delta can support controlled **Schema Evolution**, allowing the table schema to change when required.

### Schema Enforcement vs Schema Evolution

**Schema Enforcement**

> Protects the existing schema from incompatible data.

**Schema Evolution**

> Allows intentional changes to the schema.

### Difference to Remember

| Concept | Purpose |
|---|---|
| **Schema Enforcement** | Prevent unwanted/incompatible schema changes |
| **Schema Evolution** | Allow legitimate schema changes when required |

This distinction is useful for interviews.

---

## 3.14 CRUD Operations with Delta

Delta tables support operations that are much more difficult to manage reliably with ordinary files.

CRUD means:

- **Create**
- **Read**
- **Update**
- **Delete**

Delta also supports operations such as **MERGE**, which is very useful in data engineering.

### MERGE / Upsert Example

Suppose incoming customer data contains both existing and new customers.

```text
Existing Customer
       ↓
Update Record

New Customer
       ↓
Insert Record
```

This can be handled using a **MERGE / Upsert** pattern.

### Why Delta Helps

Delta provides the transaction and table-management layer required to perform operations such as:

- Insert
- Update
- Delete
- Merge

more reliably than working directly with independent files.

## 3.15 SQL Querying in a Fabric Lakehouse

Fabric Lakehouse tables can also be accessed through a **SQL analytics endpoint**.

This is useful because different personas can work with the same Lakehouse using different technologies.

### Data Engineer

Uses:

```text
PySpark / Notebook
```

### Data Analyst

Uses:

```text
SQL
```

### BI Developer

Uses:

```text
Power BI
```

This demonstrates an important Fabric concept:

> **The same underlying data can support different analytical experiences without every team creating separate copies.**

### SQL Example from My Practice

A practical query used during learning was:

```sql
SELECT
    ProductCategory,
    SUM(Revenue) AS Total_Revenue,
    COUNT(*) AS Total_Orders
FROM tbl_sales_data
GROUP BY ProductCategory
ORDER BY Total_Revenue DESC;
```

This returned:

- Product Category
- Total Revenue
- Total Orders

for each product category.

This demonstrated that after loading data into a **Delta Table in the Fabric Lakehouse**, I could query that data using SQL and perform business aggregations.

### Lakehouse and the Medallion Architecture

Lakehouse and Delta tables also become important when implementing:

```text
Bronze
   ↓
Silver
   ↓
Gold
```

### Bronze

Raw or landing data.

### Silver

Cleaned and transformed data.

### Gold

Business-ready analytical data.

Delta provides reliable tables for moving and managing data across these layers.

The Medallion Architecture is covered separately in detail.

## 3.16 Interview Understanding

### What is a Lakehouse?

A Lakehouse combines the flexibility of a Data Lake with analytical and table-management capabilities traditionally associated with a Data Warehouse.

In Microsoft Fabric, Lakehouse data is stored in OneLake and can be accessed using technologies such as:

- Spark
- SQL
- Power BI

### What is a Delta Table?

A Delta table stores its underlying data in **Parquet files** and maintains a **Delta transaction log**.

The transaction layer provides capabilities such as:

- ACID transactions
- Schema enforcement
- Versioning
- Time travel
- Reliable updates and deletes

### What is the difference between Parquet and Delta?

> **Parquet is a columnar file format, whereas Delta uses Parquet files plus a transaction log to provide reliable table-management capabilities such as ACID transactions and versioning.**

### What are ACID transactions?

ACID stands for:

> **Atomicity → Consistency → Isolation → Durability**

These properties help ensure reliable and consistent data operations.

### What is the difference between Files and Tables in a Fabric Lakehouse?

**Files** are used for storing general or raw files such as:

- CSV
- JSON
- Parquet

**Tables** represent structured analytical tables, commonly using Delta.

### Why is Delta better than storing analytical tables only as CSV?

Delta provides capabilities such as:

- ACID transactions
- Schema management
- Version history
- Efficient analytical storage through Parquet
- Reliable update and delete operations

CSV does not provide these table-management capabilities.

### What is the difference between Schema Enforcement and Schema Evolution?

> **Schema Enforcement protects the expected table structure, while Schema Evolution allows controlled changes to that structure when required.**

### Why is the Lakehouse useful for different data personas?

Because the same underlying Lakehouse data can support different analytical technologies.

For example:

```text
Data Engineer → PySpark

Data Analyst → SQL

BI Developer → Power BI
```

This reduces the need for different teams to create separate copies of the same data.
