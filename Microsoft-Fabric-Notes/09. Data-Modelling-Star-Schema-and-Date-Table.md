# Chapter 9: Data Modelling, Star Schema and Date Table

---

## 9.1 What is Data Modelling?

**Data modelling means organizing data into a structure that is easy to analyze, understand and use for reporting.**

In analytics, simply having clean tables is not enough.

We also need to define:

- Which table contains business transactions
- Which tables contain descriptive information
- How tables are related
- What level of detail each table contains
- Which columns should be used for filtering and grouping
- How the model will support Power BI reporting

### Simple Understanding

> **Data Modelling = Structuring data so analytics works correctly and efficiently.**

A good analytical model organizes data according to how the business needs to analyze it rather than simply following how the source system provides it.

---

## 9.2 Why Data Modelling is Important

If data is not modelled properly, we can face issues such as:

- Duplicate calculations
- Incorrect totals
- Complex DAX
- Difficult filtering
- Ambiguous relationships
- Poor report performance
- Confusing data for users
- Difficult maintenance

A good model makes downstream reporting much easier.

Data modelling acts as an important bridge between:

```text
Data Engineering
      ↓
Data Modelling
      ↓
Business Intelligence
```

### Why Model Before Building Reports?

A common mistake is to start creating charts before designing the analytical model properly.

This can later create problems such as:

- Complicated measures
- Incorrect filtering
- Relationship problems
- Table rework
- Poor report performance

A better process is:

```text
Understand Business Requirement
            ↓
Design Fact and Dimensions
            ↓
Create Relationships
            ↓
Validate Model
            ↓
Create Measures
            ↓
Build Report
```

### Important Principle

> **Good reporting starts with good modelling.**

## 9.3 Fact Table

A **Fact Table contains measurable business events or transactions.**

Examples include:

- Sales
- Orders
- Payments
- Bookings
- Claims
- Transactions

A Sales Fact table might contain:

| DateKey | ProductKey | CustomerKey | Quantity | Revenue |
|---:|---:|---:|---:|---:|
| 20260816 | 101 | 5001 | 2 | 70000 |

Fact tables mainly contain:

- Keys
- Numeric measures
- Transaction or event-level data

### Simple Understanding

> **Fact = What happened?**

Examples:

```text
A Product Was Sold

A Booking Was Made

A Payment Was Processed
```

### Typical Measures in a Fact Table

Examples include:

- Revenue
- Quantity
- Cost
- Discount
- Transaction amount

---

## 9.4 Dimension Table

A **Dimension Table contains descriptive information used to analyze Facts.**

### Product Dimension

```text
dim_product
```

May contain:

- ProductKey
- ProductName
- Category
- Brand

### Customer Dimension

```text
dim_customer
```

May contain:

- CustomerKey
- CustomerName
- City
- Segment

### Date Dimension

```text
dim_date
```

May contain:

- DateKey
- Date
- Day
- Month
- Quarter
- Year

### Region Dimension

```text
dim_region
```

May contain:

- RegionKey
- Region
- Country

### Simple Understanding

> **Dimension = How do I want to analyze the Fact?**

For example:

```text
Revenue by Product

Revenue by Customer

Revenue by Month

Revenue by Region
```

### Dimension Attributes

Dimension tables contain attributes used for:

- Filtering
- Grouping
- Slicing
- Categorizing analytical data

For example, `dim_product` may contain:

```text
Product
Category
Brand
```

These attributes allow analysis such as:

```text
Revenue by Category

Revenue by Brand
```

---

## 9.5 Fact vs Dimension

The difference between Fact and Dimension tables is fundamental to dimensional modelling.

| Fact Table | Dimension Table |
|---|---|
| Contains business events | Contains descriptive attributes |
| Usually contains numeric measures | Usually contains descriptive columns |
| Often contains many rows | Usually contains fewer rows |
| Commonly contains foreign keys | Commonly contains unique dimension keys |
| Example: Sales | Example: Product |
| Answers "What happened?" | Answers "By what / who / where / when?" |

### Easy Way to Remember

> **Fact = Numbers + Events**

> **Dimension = Description + Context**

### Example

Fact:

```text
Revenue = 70,000
```

Dimensions explain:

```text
Which Product?
Which Customer?
Which Date?
Which Region?
```

## 9.6 Star Schema

A **Star Schema is a dimensional modelling design where a central Fact table connects directly to multiple Dimension tables.**

Conceptually:

```text
             dim_product
                  |
                  |
dim_customer — fact_sales — dim_date
                  |
                  |
              dim_region
```

The structure resembles a star, which is why it is called a **Star Schema**.

### Example Without Proper Modelling

Suppose a Sales table contains everything:

```text
OrderID
Customer
City
Product
Category
Date
Revenue
```

The same descriptive values may repeat thousands or millions of times.

For example:

```text
Customer A
```

may occur across hundreds of transactions.

Similarly:

```text
Laptop
```

may occur across thousands of Sales rows.

### Example With Star Schema

Instead, we can separate the data.

**Fact Sales**

| OrderID | CustomerKey | ProductKey | DateKey | Revenue |
|---:|---:|---:|---:|---:|
| 101 | 1001 | 501 | 20260816 | 70000 |

**Customer Dimension**

| CustomerKey | Customer | City |
|---:|---|---|
| 1001 | Customer A | Mumbai |

**Product Dimension**

| ProductKey | Product | Category |
|---:|---|---|
| 501 | Laptop | Electronics |

**Date Dimension**

| DateKey | Date | Month | Year |
|---:|---|---|---:|
| 20260816 | 16-Aug-2026 | August | 2026 |

Now:

- Transactions remain in the Fact table
- Descriptive information remains in Dimensions

This creates a much cleaner analytical structure.

---

## 9.7 Why Use a Star Schema?

Star Schema is widely used in analytics because it provides:

- Simple relationships
- Better model readability
- Easier filtering
- Easier DAX
- Better reporting experience
- Better maintainability
- Better analytical performance in many scenarios

It separates:

```text
Business Measurements
        ↓
      Facts
```

from:

```text
Business Descriptions
        ↓
     Dimensions
```

### Why Star Schema Helps Power BI

A well-designed Star Schema can make Power BI models easier to understand.

Benefits include:

- Dimensions provide clean slicers
- Measures operate over Fact tables
- Filter direction is easier to understand
- Business logic becomes more maintainable
- Report developers can understand the model quickly

### Practical Principle

> **For analytical reporting, organize business events into Facts and descriptive attributes into reusable Dimensions.**

## 9.8 Relationships

Tables in a model are connected through **Relationships**.

For example:

```text
dim_product[ProductKey]
          ↓
fact_sales[ProductKey]
```

The Product Dimension generally contains one row per Product.

The Fact table can contain many Sales transactions for the same Product.

Therefore, the relationship is normally:

> **Dimension (1) → Fact (*)**

### Simple Relationship Flow

```text
Dimension
    ↓
Relationship
    ↓
Fact Table
```

Relationships allow dimensions to filter and analyze Fact data.

---

## 9.9 One-to-Many Relationship

A **One-to-Many relationship** is the most common relationship pattern in a Star Schema.

### Product Dimension

| ProductKey | Product |
|---:|---|
| 1 | Laptop |
| 2 | Mobile |

### Fact Sales

| OrderID | ProductKey | Revenue |
|---:|---:|---:|
| 101 | 1 | 70000 |
| 102 | 1 | 70000 |
| 103 | 2 | 30000 |

`ProductKey = 1` occurs once in the Product Dimension but can occur many times in Fact Sales.

Therefore:

```text
dim_product
     1
     ↓
     *
fact_sales
```

### Standard Star Schema Pattern

> **Dimension (1) → Fact (*)**

This is the relationship design we generally aim for where appropriate.

---

## 9.10 Primary Key and Foreign Key

Primary and Foreign Keys help connect Fact and Dimension tables.

### Primary Key

A **Primary Key** uniquely identifies a row.

Example:

```text
dim_product[ProductKey]
```

Each Product should have a unique ProductKey.

### Foreign Key

A **Foreign Key** is the corresponding key stored in another table.

Example:

```text
fact_sales[ProductKey]
```

### Relationship

```text
dim_product.ProductKey
          ↓
fact_sales.ProductKey
```

This allows each Sales transaction to connect to its descriptive Product information.

### Simple Understanding

> **Primary Key = Unique identifier**

> **Foreign Key = Matching key used to create the relationship**

---

## 9.11 Surrogate Keys

In dimensional modelling, Dimension tables often use **Surrogate Keys**.

A Surrogate Key is a generated technical identifier rather than relying directly on a source-system business key.

Example source Product ID:

```text
PROD-A102
```

Warehouse Surrogate Key:

```text
ProductKey = 25
```

### Why Use Surrogate Keys?

They can help with:

- Managing dimension changes
- Integrating multiple source systems
- Slowly Changing Dimensions
- Stable model relationships

For simpler learning projects, source or natural keys may sometimes be sufficient.

However, Surrogate Keys are an important concept in production dimensional modelling.

### Simple Understanding

> **Business Key = Comes from business/source system**

> **Surrogate Key = Technical key generated for the analytical model**

---

## 9.12 Fact Table Grain

One of the most important modelling decisions is defining the **Grain** of the Fact table.

Grain means:

> **What does one row represent?**

### Sales Fact Example

One row per:

```text
Order Line
```

### Daily Sales Fact

One row per:

```text
Product + Store + Day
```

### Monthly Summary Fact

One row per:

```text
Product + Region + Month
```

Before designing a Fact table, the grain should be clearly defined.

### Important Rule

> **Do not mix different grains in the same Fact table without a deliberate design reason.**

### Example of a Grain Problem

Suppose some rows represent:

```text
Individual Orders
```

while other rows represent:

```text
Monthly Totals
```

If we calculate:

```text
SUM(Revenue)
```

we may double-count data.

Therefore, one of the first questions when designing a Fact table should be:

> **What exactly does one row represent?**

This is one of the most important real-world modelling questions.

## 9.13 Date Dimension

A **Date Dimension is a dedicated table containing a continuous range of dates and useful date attributes.**

Typical columns include:

- Date
- Day
- Day Name
- Week
- Month Number
- Month Name
- Quarter
- Year
- Financial Year
- Weekend / Weekday flag

Example:

| Date | Day | Month | Quarter | Year |
|---|---:|---|---|---:|
| 01-Jan-2026 | 1 | January | Q1 | 2026 |
| 02-Jan-2026 | 2 | January | Q1 | 2026 |
| 03-Jan-2026 | 3 | January | Q1 | 2026 |

### Fact Table Relationship

The relationship generally looks like:

```text
dim_date[Date]
      1
      ↓
      *
fact_sales[OrderDate]
```

This means one Date can correspond to many Sales transactions.

Power BI can then use Date Dimension fields such as:

- Month
- Quarter
- Year

to analyze measures from the Fact table.

---

## 9.14 Why We Need a Date Dimension

A Date Dimension makes time-based analysis much easier.

It allows analysis such as:

- Revenue by Month
- Revenue by Quarter
- Year-over-Year growth
- Month-over-Month growth
- Weekday vs Weekend
- Financial Year analysis
- Trends over time

It also provides consistent calendar attributes across the model.

### Why Not Use Only the Fact Table Date?

We can use the transaction date directly for simple analysis.

However, a dedicated Date Dimension provides:

- Continuous dates
- Consistent Month / Quarter / Year attributes
- Fiscal calendars
- Week definitions
- Custom sorting
- Time intelligence
- Reusable date filtering

Therefore:

> **Date Dimension provides a proper analytical calendar rather than relying only on transaction dates.**

---

## 9.15 Continuous Dates

One important practical learning was creating a Date table containing **all dates**, including dates where no transactions occurred.

### Example

Suppose Sales transactions exist on:

```text
1 August
2 August
4 August
```

but no Sales transaction occurred on:

```text
3 August
```

If the report uses only dates from the Fact table:

```text
1 Aug
2 Aug
4 Aug
```

3 August disappears.

With a continuous Date Dimension:

```text
1 Aug
2 Aug
3 Aug
4 Aug
```

3 August can still appear in the reporting timeline.

### Why Missing Dates Matter

Suppose a report displays:

| Date | Revenue |
|---|---:|
| 1 Aug | 1000 |
| 2 Aug | 1200 |
| 4 Aug | 1500 |

Without 3 August, the viewer may not know whether:

- No transaction happened
- Data is missing
- A filter removed the date
- Data failed to load

A continuous Date Dimension makes the timeline more reliable.

### Important Rule

> **A Date Dimension should normally contain a continuous date range rather than only dates present in the Fact table.**

### Date Table Does Not Create Missing Transactions

This distinction is important.

If there were no Sales on 3 August:

```text
dim_date
   ↓
3 August Exists
```

but:

```text
fact_sales
   ↓
No Sales Row Exists
```

The report can then represent the value appropriately as:

```text
0
```

or:

```text
Blank
```

depending on the measure and visualization.

Therefore:

> **Date Table fills the calendar, not the transactions.**

## 9.16 Measures and Filter Flow

The model eventually needs business **Measures**.

Examples include:

### Total Revenue

```text
SUM(Revenue)
```

### Total Orders

```text
COUNT(OrderID)
```

### Average Order Value

```text
Total Revenue / Total Orders
```

Measures are evaluated according to the filter context coming from Dimension tables.

### Example

A general measure:

```text
Total Revenue
```

can become:

```text
Revenue for Mumbai
```

or:

```text
Revenue for Laptop
```

or:

```text
Revenue for January
```

depending on the active filters.

### Filter Flow

Conceptually:

```text
Dimension
    ↓
Filters
    ↓
Fact Table
    ↓
Measure
```

Example:

```text
User Selects:
Category = Electronics
          ↓
dim_product
          ↓
Filters
          ↓
fact_sales
          ↓
Total Revenue
          ↓
Electronics Revenue
```

### Important Modelling Rule

> **Dimensions filter Facts; Measures summarize Facts.**

This is one of the most useful modelling rules to remember.

---

## 9.17 Many-to-Many Relationships

A **Many-to-Many relationship** can occur when both related tables contain duplicate values in the relationship columns.

Many-to-Many relationships are sometimes required, but they can make models:

- More complex
- Harder to understand
- More difficult to troubleshoot
- More difficult to reason about

A well-designed Star Schema generally prefers:

> **Dimension (1) → Fact (*)**

where appropriate.

### Important Principle

> **Do not use Many-to-Many simply because Power BI allows it.**

Use it only when the business and data model genuinely require it.

---

## 9.18 Bi-Directional Filtering

Relationships can sometimes allow filters to travel in both directions.

This is known as **Bi-Directional Filtering**.

It may be useful in specific scenarios.

However, unnecessary bi-directional filtering can cause:

- Ambiguous filter paths
- Unexpected calculations
- Harder debugging
- A more difficult model to understand

### Good Modelling Principle

> **Keep relationships as simple as possible and use bi-directional filtering only when the business requirement justifies it.**

For a normal Star Schema, simpler filter flow is generally easier to maintain and troubleshoot.

---

## 9.19 Star Schema vs Flat Table

### Flat Table

A Flat Table keeps most information in one large table.

Advantages:

- Simple initially
- Can be convenient for very small datasets

Disadvantages:

- Repeated descriptive values
- Larger data size
- Difficult maintenance
- Difficult reuse
- Less clean analytical logic

### Star Schema

Star Schema separates Facts and Dimensions.

Advantages:

- Cleaner analytical model
- Reusable Dimensions
- Easier filtering
- Easier maintenance
- Better suited to BI models
- Easier model understanding

### Practical Rule

> **For analytical models, a well-designed Star Schema is generally preferable to one giant Flat Table.**

---

## 9.20 Star Schema vs Snowflake Schema

A **Snowflake Schema** further normalizes Dimension tables.

### Star Schema

Dimensions generally connect directly to the Fact table.

```text
             dim_product
                  |
                  |
dim_customer — fact_sales — dim_date
```

### Snowflake Schema

Dimensions can connect to other Dimensions.

For example:

```text
fact_sales
    |
dim_product
    |
dim_category
    |
dim_department
```

### Comparison

| Star Schema | Snowflake Schema |
|---|---|
| Dimensions connect directly to Fact | Dimensions can be further normalized |
| Simpler structure | More normalized structure |
| Easier for many BI users | Can introduce more joins |
| Often preferred for reporting simplicity | Useful where normalization is appropriate |

### Practical Understanding

> **Star = Simpler dimensional structure**

> **Snowflake = More normalized dimensional structure**

The correct choice depends on the use case.

## 9.21 Semantic Model

After data is structured, a **Semantic Model creates a business-friendly analytical layer on top of the data.**

A Semantic Model can contain:

- Tables
- Relationships
- Measures
- Hierarchies
- Business terminology
- Formatting
- Security

### Simple Understanding

> **Physical tables store data.**

> **Semantic Model tells Power BI how the business should analyze that data.**

### Semantic Model and Power BI

The complete flow can look like:

```text
Gold / Warehouse / Lakehouse
            ↓
      Semantic Model
            ↓
Fact Tables
Dimensions
Relationships
Measures
Security
            ↓
       Power BI Report
            ↓
Charts
KPIs
Slicers
Tables
            ↓
       Business User
```

This separation is useful because the business user should not need to understand the full raw data-engineering structure.

---

## 9.22 Data Model vs Semantic Model

These terms are related but are not exactly the same.

### Data Model

Focuses mainly on:

- Tables
- Structure
- Relationships
- Fact and Dimension design

Example:

```text
fact_sales
     ↓
dim_product
dim_customer
dim_date
```

### Semantic Model

Builds on the structure and adds analytical business meaning.

It can additionally include:

- Total Revenue
- Total Orders
- Average Order Value
- Business-friendly names
- Formatting
- Security
- Analytical metadata

### Simple Difference

> **Data Model = Structure**

> **Semantic Model = Structure + Business Meaning + Analytical Logic**

### Data Modelling and the Gold Layer

Gold data can be prepared in structures that support analytics.

For example:

```text
Silver Transactions
       ↓
Transform Into
       ↓
fact_sales
dim_customer
dim_product
dim_date
       ↓
Gold Analytical Model
       ↓
Semantic Model
       ↓
Power BI
```

This can be cleaner than sending one large Silver transaction table directly into every report.

### Practical Architecture

```text
Silver
   ↓
Gold Fact + Dimensions
   ↓
Relationships
   ↓
Semantic Model
   ↓
Measures
   ↓
Power BI
```

## 9.23 Interview Understanding

### What is Data Modelling?

Data Modelling means organizing data into structures and relationships that allow analytics and reporting to work correctly and efficiently.

### What is a Fact Table?

A Fact Table contains measurable business events or transactions and normally includes:

- Numeric measures
- Foreign keys
- Transaction/event-level data

### What is a Dimension Table?

A Dimension Table contains descriptive attributes used to:

- Filter
- Group
- Slice
- Analyze

Fact data.

### What is a Star Schema?

A Star Schema is a dimensional model where a central Fact table connects directly to multiple Dimension tables.

### What is the Difference Between Fact and Dimension?

> **Fact = Business Events + Measures**

> **Dimension = Descriptive Context**

### What is a One-to-Many Relationship?

It is a relationship where one Dimension row can correspond to many Fact rows.

Example:

```text
dim_product (1)
       ↓
fact_sales (*)
```

### What is Grain?

Grain defines:

> **What one row in a Fact table represents.**

For example:

```text
One Row per Order Line
```

The grain should be defined before designing the Fact table.

### What is a Surrogate Key?

A Surrogate Key is a generated technical identifier used in analytical modelling rather than relying directly on the source business key.

### Why is a Date Dimension Important?

A Date Dimension provides:

- Continuous dates
- Standard date attributes
- Month
- Quarter
- Year
- Fiscal periods
- Reusable calendar filtering

It also allows dates without transactions to remain visible on the report timeline.

### Does the Date Table Create Missing Transactions?

No.

> **Date Table fills the calendar, not the transactions.**

### What is Filter Flow?

In a typical Star Schema:

> **Dimensions filter Facts, and Measures summarize Facts.**

### Why Avoid Many-to-Many Where Possible?

Many-to-Many relationships can introduce additional complexity and make filtering or calculations more difficult to understand.

### Why Avoid Unnecessary Bi-Directional Relationships?

They can introduce:

- Ambiguous filter paths
- Unexpected calculations
- More difficult debugging

### Star Schema vs Flat Table?

A Star Schema separates Fact and Dimension data, while a Flat Table stores most information together.

For analytical models, Star Schema usually provides cleaner modelling and more reusable Dimensions.

### Star Schema vs Snowflake Schema?

Star Schema keeps Dimensions more directly connected to the Fact.

Snowflake Schema further normalizes Dimensions into additional related tables.

### What is a Semantic Model?

A Semantic Model is the business-friendly analytical layer used by Power BI.

It can contain:

- Tables
- Relationships
- Measures
- Formatting
- Security
- Business terminology

### Data Model vs Semantic Model?

> **Data Model = Structure**

> **Semantic Model = Structure + Business Meaning + Analytical Logic**

### Why Design the Model Before the Report?

Because poor modelling can create:

- Complex measures
- Incorrect filters
- Incorrect totals
- Poor performance
- Difficult report maintenance

Therefore:

> **Good reporting starts with good modelling.**

### Practical Example

Suppose Silver Sales contains:

```text
OrderID
Date
Customer
City
Product
Category
Revenue
```

Instead of directly using one large table, we create:

```text
fact_sales
dim_date
dim_customer
dim_product
```

Then build relationships:

```text
             dim_product
                  |
                  |
dim_customer — fact_sales — dim_date
```

Power BI can now answer questions such as:

- Revenue by Product
- Revenue by Category
- Revenue by Customer
- Revenue by City
- Revenue by Month
- Revenue by Year

### Real-World Understanding

The important learning is not:

> **I created relationships between tables.**

A stronger understanding is:

> **I modelled business data into Fact and Dimension tables using a Star Schema, defined the grain of the Fact table, created one-to-many relationships and used a continuous Date Dimension so reporting remains consistent even when some dates have no transactions.**

## 9.24 Key Takeaways

1. **Data Modelling organizes data so it can be analyzed correctly and efficiently.**

2. The two main table types are:

   > **Fact = Business Events / Measures**

   > **Dimension = Descriptive Context**

3. A **Star Schema** contains a central Fact table surrounded by Dimension tables.

4. A common relationship pattern is:

   > **Dimension (1) → Fact (*)**

5. Primary and Foreign Keys connect Fact and Dimension tables.

6. Surrogate Keys are generated technical identifiers commonly used in dimensional models.

7. Before designing a Fact table, always define its **Grain**:

   > **What does one row represent?**

8. Do not mix different grains without a clear design reason.

9. A **Date Dimension** provides a proper analytical calendar.

10. A Date Dimension should normally contain a **continuous range of dates**.

11. Dates without transactions can still appear on the reporting axis when using a continuous Date Dimension.

12. A Date table does not create missing business transactions:

   > **Date Table fills the calendar, not the transactions.**

13. A key modelling rule is:

   > **Dimensions filter Facts → Measures summarize Facts**

14. Prefer simple **One-to-Many relationships** where appropriate.

15. Avoid unnecessary:

   - Many-to-Many relationships
   - Bi-Directional filtering

16. Star Schema generally provides a cleaner analytical structure than one large Flat Table.

17. Snowflake Schema further normalizes Dimension tables.

18. A **Semantic Model** adds business meaning and analytical logic on top of the data structure.

19. The key distinction is:

   > **Data Model = Structure**

   > **Semantic Model = Structure + Business Meaning + Analytical Logic**

20. Gold data can be organized into:

```text
Fact Tables
     +
Dimension Tables
     ↓
Relationships
     ↓
Semantic Model
     ↓
Power BI
```

21. The complete analytical flow is:

> **Silver → Gold Fact/Dimensions → Relationships → Semantic Model → Measures → Power BI Report**

22. The most important principle is:

> **Do not build the report first and fix the data model later. Build a clean analytical model first, because good reporting starts with good modelling.**
