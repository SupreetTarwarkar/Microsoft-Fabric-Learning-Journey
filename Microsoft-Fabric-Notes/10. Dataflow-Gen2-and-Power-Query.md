# Chapter 10: Dataflow Gen2 and Power Query

---

## 10.1 Dataflow Gen2

**Dataflow Gen2 is a low-code data ingestion and transformation capability in Microsoft Fabric that uses the Power Query experience.**

It allows us to:

- Connect to data sources
- Import data
- Clean data
- Transform data
- Combine datasets
- Change data types
- Remove unwanted records
- Create calculated columns
- Load transformed data into supported Fabric destinations

### Simple Understanding

> **Dataflow Gen2 = Power Query-based data ingestion and transformation in Microsoft Fabric.**

Dataflow Gen2 can be especially familiar to people who already use:

- Power BI Power Query
- Excel Power Query

because many of the same transformation concepts apply.

### Basic Flow

```text
Source
   ↓
Dataflow Gen2
   ↓
Power Query
   ↓
Transform
   ↓
Fabric Destination
```

---

## 10.2 Why Use Dataflow Gen2?

Not every transformation requires PySpark or complex code.

Many common data-cleaning operations can be performed through a graphical low-code interface.

Examples include:

- Remove columns
- Rename columns
- Change data types
- Filter rows
- Replace values
- Remove duplicates
- Handle null values
- Split columns
- Merge tables
- Append tables
- Create conditional columns
- Create custom columns
- Group data

Instead of writing code for every transformation, these operations can often be created through the Power Query interface.

### Why It Can Be Useful

Dataflow Gen2 can be useful when:

- Power Query is sufficient for the transformation
- Analysts already understand Power Query
- A low-code approach improves maintainability
- Standard data-cleaning operations are required
- The transformation does not require complex Spark engineering

### Important Principle

> **Choose the simplest tool that reliably meets the workload requirements.**

Dataflow Gen2 does not automatically replace Notebooks, and Notebooks do not make Dataflow Gen2 unnecessary.

---

## 10.3 Dataflow Gen2 vs Notebook

Both Dataflow Gen2 and Fabric Notebooks can transform data, but they provide different development experiences.

| Dataflow Gen2 | Notebook |
|---|---|
| Low-code | Code-based |
| Uses Power Query | Uses PySpark / Python / Spark SQL |
| Graphical interface | Notebook cells |
| Familiar to Power BI / Excel users | Familiar to Engineers / Developers |
| Good for standard transformations | Strong for complex engineering |
| Easier for many analysts | Greater coding flexibility |

### Simple Understanding

> **Dataflow Gen2 = Low-Code Transformation**

> **Notebook = Code-Based Transformation**

### When Might I Use Dataflow Gen2?

Examples:

- Change data types
- Standardize values
- Merge datasets
- Append files
- Remove unwanted columns
- Create conditional logic
- Perform Power Query-based transformations

### When Might I Use a Notebook?

Examples:

- Large-scale Spark processing
- Complex PySpark logic
- Advanced engineering transformations
- Distributed data processing
- More flexible code-based workflows

### Dataflow Gen2 Does Not Replace Data Engineering

It would be incorrect to say:

> **If Dataflow Gen2 exists, we do not need Notebooks.**

It would also be incorrect to say:

> **If we know PySpark, Dataflow Gen2 is useless.**

The better approach is:

> **Choose based on complexity, scale, team skills, maintainability and business requirements.**

## 10.4 Power Query

**Power Query is Microsoft's data connection and transformation technology.**

It allows us to connect to data and perform transformation steps before loading the result into a destination.

### Typical Flow

```text
Source
   ↓
Power Query
   ↓
Transform
   ↓
Destination
```

Power Query records transformations as a sequence of steps.

Example:

```text
Source
   ↓
Promoted Headers
   ↓
Changed Type
   ↓
Removed Columns
   ↓
Filtered Rows
   ↓
Removed Duplicates
```

Each transformation builds on the previous step.

### Why Power Query is Useful

Power Query provides a visual way to:

- Inspect data
- Clean data
- Reshape data
- Combine datasets
- Apply repeatable transformation logic

---

## 10.5 Power Query M Language

Behind Power Query transformations is the **M language**.

When transformations are created through the graphical interface, Power Query generates M expressions representing those steps.

For example:

- Changing a data type
- Filtering rows
- Removing a column
- Creating a calculated column

all generate corresponding M logic.

### Important

For many normal transformations, I do not need to manually write M code.

However, it is useful to understand that:

> **Power Query = Transformation interface / engine**

> **M = Language behind Power Query transformations**

Knowledge of M becomes more useful when more customized transformation logic is required.

## 10.6 Connecting to Data Sources

The first step in Dataflow Gen2 is generally selecting and connecting to a data source.

Depending on the scenario, sources can include:

- SQL databases
- Files
- Cloud storage
- Web / API sources
- Fabric data
- Other supported connectors

### Conceptual Flow

```text
Data Source
     ↓
Connection
     ↓
Dataflow Gen2
     ↓
Power Query
     ↓
Transformation
     ↓
Destination
```

### Query Preview

After connecting to the source, Power Query provides a preview of the data.

Example:

| OrderID | Customer | Status | Revenue |
|---:|---|---|---:|
| 101 | A | Completed | 500 |
| 102 | B | Cancelled | 600 |
| 103 | C | Returned | 300 |

The preview helps us inspect the source before applying transformations.

### Important

> **Preview looking correct does not automatically guarantee that the final destination data is correct.**

The final output should still be validated after the Dataflow runs.

---

## 10.7 Applied Steps

Power Query records transformations under **Applied Steps**.

For example:

```text
Source
   ↓
Navigation
   ↓
Changed Type
   ↓
Filtered Rows
   ↓
Removed Columns
   ↓
Removed Duplicates
```

This makes the transformation logic easier to understand and troubleshoot.

### Why Applied Steps Matter

Applied Steps help us see:

- What transformations were performed
- In what order they were performed
- Where an incorrect transformation may have started
- How the final result was created

If a transformation produces unexpected data, we can inspect the steps one by one.

### Important Principle

> **Applied Steps provide a visible transformation history for the query.**

## 10.8 Changing Data Types

Assigning correct data types is one of the most important Power Query transformations.

Examples:

```text
OrderDate
Text → Date
```

```text
Revenue
Text → Decimal Number
```

```text
Quantity
Text → Whole Number
```

### Why Data Types Matter

Incorrect data types can create problems with:

- Calculations
- Sorting
- Filtering
- Relationships
- Aggregations
- Date analysis

### Example

If:

```text
Revenue = "1500"
```

is stored as Text, numerical calculations may not behave correctly.

It should normally use an appropriate numeric data type.

### Important

Correct data types should be established before downstream modelling and analytics.

---

## 10.9 Filtering Rows

Power Query can remove records that do not meet business requirements.

### Example

Original data:

| OrderID | Status | Revenue |
|---:|---|---:|
| 101 | Completed | 500 |
| 102 | Cancelled | 600 |
| 103 | Returned | 300 |
| 104 | Completed | 0 |

Business rules:

- Remove Cancelled
- Remove Returned
- Remove Revenue = 0

Result:

| OrderID | Status | Revenue |
|---:|---|---:|
| 101 | Completed | 500 |

### Important Principle

> **Filtering should follow business rules, not personal assumptions about which records look unnecessary.**

This transformation is conceptually similar to filtering data using PySpark.

The main difference is how the logic is created.

---

## 10.10 Removing Columns

Source systems often contain fields that are not required for downstream analytics.

Example:

```text
OrderID
CustomerID
ProductID
Revenue
InternalComment
TemporaryField
ImportFlag
```

If only the first four columns are needed downstream, unnecessary columns can be removed.

### Benefits

Removing unnecessary columns can improve:

- Readability
- Maintainability
- Dataset simplicity
- Downstream modelling

### Important Medallion Principle

Do not unnecessarily remove source information from the raw Bronze layer if that information may be needed for:

- Auditing
- Reprocessing
- Troubleshooting

Cleaning and removal are generally more appropriate in later layers.

---

## 10.11 Renaming Columns

Source systems may contain technical or unclear column names.

For example:

```text
ord_dt
cust_id
rev_amt
```

These can be renamed to:

```text
OrderDate
CustomerID
RevenueAmount
```

### Why Clear Naming Matters

Clear naming improves:

- Readability
- Maintainability
- Collaboration
- Data modelling
- Business understanding

### Practical Principle

> **Use clear and consistent names that make the meaning of the data easy to understand.**

---

## 10.12 Removing Duplicates

Power Query provides functionality for removing duplicate rows.

Example:

| OrderID | Revenue |
|---:|---:|
| 101 | 500 |
| 101 | 500 |
| 102 | 700 |

If `OrderID` should uniquely identify a business transaction, duplicate handling may be required.

### Important

Do not remove records simply because they appear identical.

First understand:

> **What is the business key?**

Two similar rows may sometimes represent legitimate separate transactions.

Duplicate removal should therefore be based on:

- Business keys
- Transaction IDs
- Source-system logic
- Business requirements

---

## 10.13 Handling Null Values

Power Query can help manage missing values.

Possible actions include:

- Replace null
- Remove rows
- Fill down
- Fill up
- Keep the null
- Create a conditional flag

The correct treatment depends on business meaning.

### Example

Missing:

```text
CustomerMiddleName
```

may be acceptable.

Missing:

```text
Revenue
```

may require investigation.

### Important Principle

> **Null handling should follow business rules, not a blanket "remove all nulls" rule.**

---

## 10.14 Replace Values

Power Query can standardize inconsistent values.

Example source values:

```text
Mumbai
MUMBAI
mumbai
```

can potentially be standardized to:

```text
Mumbai
Mumbai
Mumbai
```

Another example:

```text
M
Male
MALE
```

may be standardized to:

```text
Male
```

when that matches the business definition.

### Why Replace Values?

Standardization helps improve:

- Data quality
- Grouping
- Filtering
- Reporting consistency
- Dimensional modelling

---

## 10.15 Split Column

Sometimes one column contains multiple pieces of information.

Example:

```text
Supreet Tarwarkar
```

could be split into:

```text
FirstName | LastName
```

Another example:

```text
Mumbai-Maharashtra
```

could become:

```text
City | State
```

when the delimiter and business structure are reliable.

### Typical Split Methods

Columns may be split using:

- Delimiters
- Character positions
- Other supported rules

### Important

The split logic should reflect the actual structure of the data.

---

## 10.16 Conditional Column

A **Conditional Column** creates new values based on rules.

Example:

```text
Revenue >= 100000 → High
Revenue >= 50000  → Medium
Else              → Low
```

Result:

| Revenue | RevenueCategory |
|---:|---|
| 120000 | High |
| 70000 | Medium |
| 25000 | Low |

This is conceptually similar to:

- IF logic
- CASE logic

### Simple Understanding

> **Conditional Column = Create values using business conditions.**

---

## 10.17 Custom Column

A **Custom Column** allows a new column to be created using an expression.

Example:

```text
Revenue = Quantity × UnitPrice
```

Other business calculations can also be created.

### Conditional Column vs Custom Column

**Conditional Column**

Primarily:

> Rule-based IF / ELSE logic through the interface

**Custom Column**

Primarily:

> More flexible expression-based calculation

### Simple Difference

> **Conditional Column = Rule-Based**

> **Custom Column = Expression-Based**

---

## 10.18 Merge Queries

**Merge Queries combines tables horizontally using matching keys.**

It is conceptually similar to a SQL **JOIN**.

### Example

Sales:

| ProductID | Revenue |
|---|---:|
| P01 | 500 |
| P02 | 700 |

Product:

| ProductID | ProductName |
|---|---|
| P01 | Laptop |
| P02 | Mobile |

After Merge:

| ProductID | Revenue | ProductName |
|---|---:|---|
| P01 | 500 | Laptop |
| P02 | 700 | Mobile |

### Easy Way to Remember

> **Merge = JOIN**

Merge adds related columns by matching keys between datasets.

---

## 10.19 Append Queries

**Append Queries combines rows from multiple datasets.**

### Example

January Sales:

| OrderID | Revenue |
|---:|---:|
| 101 | 500 |
| 102 | 600 |

February Sales:

| OrderID | Revenue |
|---:|---:|
| 201 | 700 |
| 202 | 800 |

Append result:

| OrderID | Revenue |
|---:|---:|
| 101 | 500 |
| 102 | 600 |
| 201 | 700 |
| 202 | 800 |

### Easy Way to Remember

> **Append = Add Rows**

This is conceptually similar to combining compatible datasets vertically.

---

## 10.20 Merge vs Append

Merge and Append solve different problems.

| Merge | Append |
|---|---|
| Combines columns | Combines rows |
| Uses matching keys | Stacks datasets |
| Similar to SQL JOIN | Similar to SQL UNION |
| Example: Sales + Product | Example: January + February |

### Shortcut to Remember

> **Merge → Horizontal**

> **Append → Vertical**

Another easy rule is:

> **Merge = Add Columns**

> **Append = Add Rows**

This is an important interview distinction.

---

## 10.21 Group By

Power Query can aggregate data using **Group By**.

Example source data:

| Product | Revenue |
|---|---:|
| Laptop | 500 |
| Laptop | 700 |
| Mobile | 300 |

After Group By Product:

| Product | Total Revenue |
|---|---:|
| Laptop | 1200 |
| Mobile | 300 |

Group By operations can include:

- Sum
- Count
- Average
- Minimum
- Maximum

### Why Group By?

It can be useful when preparing:

- Summary tables
- Business-ready datasets
- Aggregated Gold data
- Analytical outputs

### Important

The level of aggregation should follow the required business grain.

## 10.22 Dataflow Gen2 Destination

After transformation, Dataflow Gen2 needs to write the result to an appropriate destination.

Depending on the Fabric scenario, destinations can include supported Fabric data stores such as:

- Lakehouse
- Warehouse
- Other supported destinations

### Basic Flow

```text
Source
   ↓
Dataflow Gen2
   ↓
Transform
   ↓
Destination
```

The destination should be selected according to the architecture rather than simply choosing whatever is easiest.

### Dataflow Gen2 in Medallion Architecture

Dataflow Gen2 can participate in:

```text
Bronze
   ↓
Dataflow Gen2
   ↓
Silver
```

For example:

- Change data types
- Remove invalid records
- Standardize values
- Remove duplicates

It can also participate in:

```text
Silver
   ↓
Dataflow Gen2
   ↓
Gold
```

For example:

- Merge business tables
- Add classifications
- Group data
- Create business-ready structures

### Important

> **The correct placement depends on the transformation requirement and architecture.**

## 10.23 Dataflow Gen2 and Pipeline

Dataflow Gen2 can participate as an activity inside a Fabric Pipeline.

Example:

```text
Pipeline
   ↓
Copy Data
   ↓
Dataflow Gen2
   ↓
Notebook
   ↓
Warehouse
```

This allows Dataflow Gen2 to become part of a complete automated workflow.

### Can Dataflow Gen2 Be Scheduled?

Yes.

Conceptually:

```text
Schedule
   ↓
Dataflow Gen2
   ↓
Connect to Source
   ↓
Transform
   ↓
Load Destination
```

This makes Dataflow Gen2 useful for recurring processing.

### Dataflow Gen2 vs Pipeline

These should not be confused.

**Dataflow Gen2**

Primarily:

> **Transforms data**

**Pipeline**

Primarily:

> **Orchestrates the workflow**

Conceptually:

```text
Pipeline
   ↓
Runs Dataflow Gen2
```

Therefore:

> **Dataflow Gen2 can be one step inside a Pipeline.**

### Dataflow Gen2 vs Copy Activity

**Copy Activity**

Primarily:

```text
Source → Destination
```

Used to move data.

**Dataflow Gen2**

Primarily:

```text
Source → Transform → Destination
```

Used when Power Query-based transformations are required.

### Core Fabric Tool Comparison

| Requirement | Tool |
|---|---|
| Move data | **Copy Activity** |
| Low-code transformation | **Dataflow Gen2** |
| PySpark / code transformation | **Notebook** |
| Coordinate everything | **Pipeline** |

### Easy Rule

> **Copy = Move**

> **Dataflow Gen2 = Low-Code Transform**

> **Notebook = Code Transform**

> **Pipeline = Coordinate**

### Practical Architecture Example

Suppose Customer data comes from SQL.

```text
Pipeline Starts
      ↓
Dataflow Gen2
      ↓
Connect to SQL
      ↓
Power Query
      ↓
Remove Unnecessary Columns
Correct Data Types
Standardize City Names
Remove Invalid Records
Handle Duplicates
      ↓
Silver
      ↓
Notebook Processes Large Sales Data
      ↓
Gold Business Tables
      ↓
Warehouse / Semantic Model
      ↓
Power BI
```

This demonstrates that Dataflow Gen2 and Notebook can coexist within the same Fabric solution.

## 10.24 Query Folding

**Query Folding is the ability of Power Query, where supported, to translate transformation steps into operations that can be executed by the source system.**

Conceptually, instead of:

```text
Bring Huge Dataset into Fabric
          ↓
Filter Data
```

Power Query may be able to push the filter toward the source:

```text
Source Filters Data
       ↓
Only Required Rows Returned
```

### Why Query Folding Can Be Useful

It can reduce:

- Data movement
- Processing
- Resource consumption

and may improve performance.

### Example

Suppose a database contains:

```text
100 Million Rows
```

but we only require:

```text
Year = 2026
```

Without effective pushdown:

```text
100 Million Rows
      ↓
Transfer
      ↓
Filter Year = 2026
```

With query folding:

```text
Database
   ↓
Filter Year = 2026
   ↓
Only Required Rows Returned
```

### Important

Not every:

- Source
- Connector
- Transformation

supports Query Folding.

Therefore:

> **Understand the concept, but do not assume every Power Query step is automatically pushed to the source.**

### Transformation Order Matters

The order of Power Query steps can affect:

- Performance
- Data volume
- Query Folding
- Readability

When appropriate, a useful pattern can be:

```text
Filter Unnecessary Rows Early
          ↓
Remove Unnecessary Columns
          ↓
Perform More Expensive Transformations
```

### Practical Principle

> **Reduce unnecessary data as early as reasonably possible while respecting the architecture's raw-data preservation requirements.**

## 10.25 Dataflow Refresh

When a Dataflow runs again, its transformation steps are reapplied to the current source data.

Conceptually:

```text
Source Updated
      ↓
Dataflow Refresh
      ↓
Transformation Steps Re-Executed
      ↓
Destination Updated
```

Therefore, Dataflow Gen2 is not only a one-time manual cleaning tool.

It can become part of a repeatable data-processing solution.

### Validation After Refresh

Just like with Notebooks:

> **Successful execution does not automatically guarantee correct business data.**

After a Dataflow refresh, validate:

- Row counts
- Null values
- Duplicate counts
- Data types
- Aggregated totals
- Destination records

### Example

Before cleaning:

```text
100,000 Rows
```

After cleaning:

```text
92,000 Rows
```

We should understand why 8,000 records were removed.

For example:

```text
3,000 Cancelled
+
2,000 Returned
+
3,000 Invalid
=
8,000 Removed
```

### Important Principle

> **Successful Refresh ≠ Automatically Correct Data**

The final output still needs validation.

## 10.26 Interview Understanding

### What is Dataflow Gen2?

Dataflow Gen2 is a low-code data ingestion and transformation capability in Microsoft Fabric based on Power Query.

It can connect to data, transform it and load the result into supported Fabric destinations.

### Why Use Dataflow Gen2?

Dataflow Gen2 is useful when common transformation requirements can be solved effectively using a low-code Power Query experience.

Examples include:

- Filtering
- Changing data types
- Merge
- Append
- Null handling
- Duplicate handling
- Group By

### What Language Does Power Query Use?

Power Query uses the **M language**.

### What is the Difference Between Dataflow Gen2 and Notebook?

> **Dataflow Gen2 provides a low-code Power Query transformation experience, while Notebook provides code-based transformations using technologies such as PySpark.**

### What are Applied Steps?

Applied Steps represent the sequence of transformations performed in Power Query.

They make it easier to understand and troubleshoot how the final dataset was produced.

### What is the Difference Between Merge and Append?

> **Merge combines columns based on matching keys, similar to a JOIN.**

> **Append combines rows from datasets, similar to a UNION.**

### What is Query Folding?

Query Folding is the ability of Power Query, where supported, to translate transformations into operations that can be executed by the underlying source system.

This can reduce unnecessary data movement and processing.

### Can Dataflow Gen2 Run Inside a Pipeline?

Yes.

Dataflow Gen2 can participate as an activity in Fabric Pipeline orchestration.

### Can Dataflow Gen2 Be Scheduled?

Yes.

It can participate in recurring or scheduled Fabric processing.

### Dataflow Gen2 vs Copy Activity?

> **Copy Activity primarily moves data.**

> **Dataflow Gen2 primarily performs Power Query-based ingestion and transformation.**

### Dataflow Gen2 vs Pipeline?

> **Dataflow Gen2 = Transform**

> **Pipeline = Orchestrate**

### Does Dataflow Gen2 Replace Notebooks?

No.

Dataflow Gen2 and Notebooks are complementary.

The choice depends on:

- Transformation complexity
- Scale
- Team skills
- Maintainability
- Business requirements

### Why Validate After Dataflow Refresh?

Because a technically successful refresh can still produce incorrect business results.

The destination data should be checked against:

- Row counts
- Business rules
- Expected totals
- Data quality requirements

### Real-World Understanding

The important learning is not simply:

> **I know Power Query.**

A stronger understanding is:

> **I understand when Dataflow Gen2 is appropriate for low-code data ingestion and transformation. I can use Power Query to clean, reshape, merge and append data, load transformed results into Fabric destinations and orchestrate Dataflow Gen2 through Fabric Pipelines.**
